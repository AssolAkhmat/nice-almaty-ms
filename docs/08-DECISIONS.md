# 08. Решения, допущения, открытые вопросы

## Принятые решения (владелец подтвердил или делегировал)

| № | Решение | Основание |
|---|---|---|
| D1 | Drizzle ORM, не Prisma | SQL-миграции, лёгкий рантайм, одинаково работает с локальным Postgres и Supabase |
| D2 | Два окружения через адаптеры, разработка на Docker, Vercel + Supabase как переключаемая цель | делегировано владельцем |
| D3 | Google Drive через OAuth владельца, а не через сервисный аккаунт | у сервисного аккаунта нет квоты хранилища, загрузка падает без Shared Drive |
| D4 | Загрузка файлов всегда двухшаговая (сессия + прямая загрузка) | лимит тела запроса ~4.5 МБ на Vercel, фото с телефона крупнее |
| D5 | Своя аутентификация за интерфейсом `AuthProvider` | вход по телефону, аккаунты создаёт суперадмин; переход на Supabase Auth возможен без переписывания |
| D6 | Авторизация в приложении, без RLS | одна точка правды по правам; RLS = вторая копия логики |
| D7 | `org_id` заложен, создание сетей в UI выключено | делегировано владельцем |
| D8 | Сброс пароля: разрешение админа + вход с любым паролем + принудительная смена | выбор владельца; осознанно слабое место, каждое использование в аудите, разрешение живёт 24 часа и одноразовое |
| D9 | Деньги — целые тенге, округление долей вверх, излишек дому | правило владельца |
| D10 | Двойная запись в бухгалтерии | иначе переводы между фондами не сходятся |
| D11 | Роль и проживание — разные сущности | админ одновременно жилец |
| D12 | Слот ротации привязан к месту (bed_id), а не к человеку | сменился жилец — позиция в цикле сохраняется |
| D13 | Web Push + PWA сразу, e-mail и SMS не делаем | выбор владельца |
| D14 | Ставки налога 3 % и эквайринга 0,95 % — настройки, не константы | ставки меняются, ответственность за значения на владельце |

## Разрешённые противоречия исходного ТЗ

| № | Противоречие | Как решено |
|---|---|---|
| C1 | «Коммуналка не взимается за дни отсутствия» против «перерасчёт недопустим» | плата за проживание всегда полная; коммуналка — по фактическим дням. Подтверждено владельцем |
| C2 | «Заморозить личный цикл отсутствующего» против «цикл считается по id кровати» | реализована детерминированная сетка по номеру недели; отсутствие даёт `needs_reassignment` и задачу админу, а не автоматический сдвиг. Личные счётчики ломают уникальность назначений |

## Решения фазы 1 (пользователи, права, аудит)

Подтверждены владельцем 6 сентября 2026, до начала реализации.

| № | Вопрос | Принято | Файлы |
|---|---|---|---|
| P1-1 | 403 или 404 при обращении к сущности чужого дома или чужой организации | **404, без различий между «нет» и «не твоё».** Иначе админ перебором id узнаёт, сколько домов в сети и какие. `403` остаётся только для случая, когда объект внутри области видимости, но действие роли не разрешено | `src/lib/authz.ts`, `src/db/repositories/*` |
| P1-2 | Где хранить счётчик попыток входа: в памяти на serverless нельзя | Таблица `rate_limits(key text primary key, window_start timestamptz, count int)`. Ключи `login:phone:+7XXXXXXXXXX` и `login:ip:X.X.X.X`, окно 15 минут, порог 10. Просроченные строки удаляются лениво при записи; отдельное задание на очистку — фаза 6. Таблицы не было в `02-DATA-MODEL.md`, вносится туда в T1.1 | `docs/02-DATA-MODEL.md`, `src/db/schema/rate-limits.ts` |
| P1-3 | Требования к паролю | Минимум 10 символов, максимум 128, требований к классам символов нет. Запрещено совпадение с номером телефона, с выданным временным паролем и с предыдущим паролем. Хеш argon2id. Проверка одинаковая на клиенте и сервере — из одной zod-схемы | `src/lib/validation/password.ts` |
| P1-4 | Как устроена матрица прав | Декларативные данные, а не код: один объект `роль × действие × область видимости` в `src/lib/permissions.ts`. `authz.ts` собственной логики не содержит и только читает его. Тесты пишутся на запреты: на каждую отрицательную ячейку — свой тест, плюс e2e на то, что админ дома A не получает ничего по дому B | `src/lib/permissions.ts`, `src/lib/authz.ts` |
| P1-5 | Чем дёргать задания планировщика на Vercel | Внешним сервисом по HTTP с заголовком `x-cron-secret`, а не `vercel.json`. Лимиты тарифа Hobby нас тогда не связывают, а эндпоинты уже идемпотентны через `job_runs`. `vercel.crons.example.json` остаётся как есть — на случай, если расписание всё же переедет на платформу | `vercel.crons.example.json`, `docs/DEPLOY-VERCEL.md` |

## Решения фазы 2 (заселение и места)

| № | Вопрос | Принято | Файлы |
|---|---|---|---|
| P2-1 | Бывает ли смена жильцов день в день | **Бывает, это штатный случай.** Прямая норма §2.3 п.3: с даты выезда место освобождается и может быть назначено другому. Полуоткрытые периоды `[заезд, выезд)` это и реализуют. Предупреждение админу не вводится: оно мешало бы обычной работе. Следствие — за общий отрезок месяца место оплачено дважды (полный месяц выехавшему по C3 плюс ручная доплата заехавшему по §1.2 п.7); это следствие правила «перерасчёт только вручную» | `src/db/period.ts`, `docs/03-BUSINESS-RULES.md` §2.3 |
| P2-2 | Отрицательный депозит при выселении | **Счёт возврата не создаётся, долг остаётся числом на архивном проживании.** Возвращать нечего: депозит израсходован ущербом. Исход `debt` в расчётном ядре отделён от `refund` и `burn` | `src/domain/deposit.ts` |
| P2-3 | Как именно останавливать команды `db:*` на нелокальной базе (указание владельца после инцидента I1) | **Обёртка `scripts/db-guard.mjs` вокруг всех скриптов `db:*`.** Перед запуском печатается цель (хост, порт, база) и источник строки — окружение оболочки или `.env`; пароль в вывод не попадает. Локальными считаются только `localhost`, `127.0.0.1`, `::1`. Нелокальный хост требует `--allow-remote=<хост>` в самой команде, и имя хоста должно совпасть с фактическим: подтверждение, забытое в алиасе, не разрешает следующую цель. `docker-compose` подтверждает свой хост `postgres` явно | `scripts/db-guard.mjs`, `scripts/db-guard.test.ts`, `package.json`, `docker-compose.yml` |
| P2-4 | Предел размера файла и список разрешённых типов: в ТЗ их нет | **10 МБ и `image/jpeg`, `image/png`, `image/webp`, `application/pdf`.** Фотография справки с телефона помещается с запасом, а всё, что умеет исполняться в браузере, в хранилище не попадает вовсе. Тип проверяется раньше размера: маленький исполняемый файл опаснее большой фотографии. Заявленный тип — слово клиента, поэтому там, где байты идут через приложение, тип сверяется по первым байтам | `src/domain/files.ts` |
| P2-5 | Жильцу нужен `house_slug` для пути хранения, а дома в его контексте доступа нет (D11) | **Дом виден через проживание, отдельной функцией `requireHouseOfResidency`.** Область видимости роли не расширяется: списка домов и чужого дома по прямой ссылке жилец по-прежнему не получает. Видимость идёт тем же условием `residencyVisibility`, на котором стоит видимость профиля и файлов, — второй копии правила нет | `src/db/repositories/houses.ts`, `src/db/repositories/residencies.ts` |
| P2-6 | Статусы HTTP под коды ошибок: `docs/06-API.md` задаёт коды, но не статусы | **401, 403, 404, 409, 422, 429, 500** для `unauthorized`, `forbidden`, `not_found`, `conflict`, `validation_error`, `rate_limited`, `internal`. `validation_error` — 422, а не 400: запрос разобран, отвергнут его смысл. Соответствие закреплено тестом: молчаливая смена статуса ломает клиентов и почти не видна в обзоре | `src/lib/api/route.ts`, `src/lib/api/route.test.ts` |
| P2-7 | `docs/06-API.md` обещает вход по Bearer-токену, но токенов никто не выпускает | **В фазе 2 вход в `/api/v1` только по сессионной cookie.** Таблицы токенов и скоупов нет; заголовок `Authorization` отвергается с внятным текстом, а не игнорируется молча: молчаливый отказ выглядит как поломка, а не как незаконченная функция. Токены — вместе с ботом (`docs/06-API.md`, «Задел под WhatsApp-бота») | `src/lib/api/route.ts` |
| P2-8 | Писать ли в журнал чтение файла: в ТЗ требования нет | **Пишется, когда файл читает не тот, кто его загрузил.** Документы жильца — медицинские справки и удостоверение; из двух прочтений выбрано осторожное. Чтение собственного файла журнал не засоряет | `src/services/files.ts` |
| P2-9 | Что делает драйвер `gdrive`, если ключей нет: падать при старте или при первом обращении | **Старт роняет схема окружения** — `STORAGE_DRIVER=gdrive` без ключей доступа не проходит разбор (четырёх в фазе 2, трёх с P7-20: корневую папку драйвер заводит сам). Драйвер, собранный без них другим путём, отвечает `error` на проверку живости и отклоняет каждую операцию с перечислением недостающих переменных. Молчаливое «ничего не делаю» исключено обоими рубежами | `src/lib/env/schema.ts`, `src/adapters/storage/index.ts` |
| P2-10 | Drive не знает путей, а архитектура задаёт путь `/{house_slug}/{residency_id}/{document_type}/` | **Ключ разворачивается в цепочку папок от `GDRIVE_ROOT_FOLDER_ID`**, найденные папки запоминаются на время жизни драйвера. Имя файла в Drive — идентификатор записи, имя от пользователя туда не попадает. Идентификатор объекта Drive сообщает только после загрузки, поэтому `externalId` у сессии пуст, а поиск идёт по имени внутри родителя | `src/adapters/storage/gdrive.ts` |
| P2-11 | Действует ли документ в день истечения | **Да, это последний годный день.** Уведомление §1.3 приходит «в день истечения»; значит просрочка начинается со следующего. Порог предупреждения — тридцать дней, как в той же норме | `src/domain/documents.ts` |
| P2-12 | Что происходит с прежней справкой при пересдаче | **Прежняя запись остаётся, действует последняя загруженная.** История загрузок — часть проверки: админ должен видеть, что справку уже отклоняли. Удаление прежней записи стёрло бы причину отклонения вместе с ней | `src/services/documents.ts` |
| P2-13 | Дата снимка в будущем | **Отвергается как ошибка ввода.** Иначе флюорография «действует» на год вперёд от несуществующего снимка. Дата сегодняшним днём принимается | `src/domain/documents.ts` |
| P2-14 | Где живёт проверка документов до появления карточки жильца (T2.13) | **На том же экране `/documents`, видом для админа.** Карточка жильца собирает всё вместе в T2.13; заводить временный экран, который потом выбрасывать, дороже, чем показать очередь проверки там же, где жилец видит свои карточки | `src/app/(app)/documents/page.tsx` |
| P2-15 | Где брать chromium для печати договора | **Системный chromium в образе, путь в `CHROMIUM_PATH`.** `puppeteer-core` своего браузера не приносит; в образ добавлены `chromium` и шрифты Noto — без них кириллица в PDF превращается в квадраты. На машине разработчика браузера может не быть вовсе: тогда печать честно отказывает, а остальное приложение работает | `Dockerfile`, `src/adapters/pdf/*` |
| P2-16 | `@sparticuz/chromium` для Vercel: ставить ли в зависимости | **Нет, подключается на стороне Vercel.** Пакет весит десятки мегабайт и нужен одной цели из двух; в Docker-образ он попадал бы мёртвым грузом. Импорт динамический и скрыт от сборщика, отсутствие пакета объясняется словами. Живого превью-деплоя не было (P0-10), поэтому ветка проверена только отказом | `src/adapters/pdf/index.ts`, `docs/DEPLOY-VERCEL.md` |
| P2-17 | Куда в договоре попадает подпись: токеном или блоком | **Блоком в конце документа.** Палитра токенов задана модулем 11 и подписи в ней нет; вводить одиннадцатый токен ради этого — расширять требования. Положение подписи не настраивается, и это осознанная плата | `src/services/contracts.ts` |
| P2-18 | Откуда берётся первый шаблон договора | **Из сида, версия 1, активный.** Без активного шаблона договор не собрать вовсе, и пустая установка спотыкалась бы на первом заселении. Правки суперадмина сид не откатывает: шаблон заводится один раз | `src/db/seed.ts` |
| P2-19 | Кто собирает и кто подписывает договор | **Собирает админ или суперадмин, подписывает только сам жилец.** Подпись личная: за жильца её не ставит никто, включая суперадмина. Подписанный договор не пересобирается — иначе подпись оказалась бы под другим текстом, чем тот, который жилец видел. «Ключи выданы» — отдельное право и отдельная отметка | `src/lib/permissions.ts`, `src/services/contracts.ts` |
| P2-20 | Сколько машинерии счетов заводить в фазе 2 | **Формы таблиц целиком, работа — только депозитная.** `invoices`, `invoice_lines`, `payments` и `deposit_transactions` заведены по модели данных сразу: менять форму дважды дороже. Работают из них счёт типа `deposit` и платежи по нему; месячная генерация, коммуналка, штрафы и скидки — фаза 3 | `src/db/schema/invoices.ts`, `src/services/deposits.ts` |
| P2-21 | Что зачисляется на депозит, если в счёте есть доплата за дни | **Только строки типа `deposit`.** Доплата за дни до 1 числа (§1.2 п.7) — плата за проживание, а не депозит, и на депозитный счёт она попасть не должна: иначе при выселении вернулись бы чужие деньги | `src/services/deposits.ts` |
| P2-22 | Второй счёт на тот же депозит | **Не выставляется.** Два счёта дают два разных ответа на вопрос «сколько внести». Отменённый счёт не мешает выставить новый | `src/services/deposits.ts` |
| P2-23 | Переплата по счёту | **Отвергается.** Инвариант 6 из `02-DATA-MODEL.md` прямо запрещает платежи сверх суммы счёта без явного флага; флага в фазе 2 нет | `src/services/deposits.ts` |
| P2-24 | Кто отмечает оплату | **Админ дома или суперадмин, не жилец.** Деньги приходят мимо приложения — Kaspi или наличные, — и подтверждает получение тот, кто их получил. Жилец видит свой счёт и остаток, но не может объявить его оплаченным | `src/lib/permissions.ts` |

Каникулы трогают только запланированное: выполненное и отменённое остаётся как есть | `src/services/rotation-calendar.ts` |
| P4-18 | Кто участвует в генеральной уборке и откуда берётся админ дома (§6.5 называет его прямо, но проживания у него нет) | **Жильцы дома плюс пользователи с ролью админа этого дома, из базы.** Из вызывающего его брать нельзя: уборку вправе запустить и суперадмин, а убирать будет всё равно админ дома. Круг участников не зависит от того, кто нажал кнопку | `src/db/repositories/rotations.ts` |
| P4-19 | Как сделать случайное распределение повторяемым (§6.5 требует детерминированности по сиду `house_id + дата`) | **Свой генератор из строки-сида и перемешивание Фишера — Йетса.** Библиотека ради тридцати строк — лишняя зависимость в сборке. Список людей сортируется перед перемешиванием: иначе расклад зависел бы от порядка, в котором база вернула жильцов, и «тот же сид» перестал бы означать «тот же результат» | `src/domain/general-cleaning.ts` |
| P4-20 | В каком порядке раздавать зоны, если у них разные группы допуска | **От самой закрытой к самой открытой.** Зона, куда пущен один человек, обязана достаться ему: при обратном порядке он ушёл бы на общую зону, а закрытая осталась бы пустой при полном доме. Порядок вывода при этом остаётся исходным — читателю показывают зоны так, как они заведены | `src/domain/general-cleaning.ts` |
| P4-21 | Где хранится переключатель «отменять обычную воскресную ротацию» | **Настройкой дома `rotations.cancelRegularOnGeneral` в общей таблице настроек.** Заводить под один флаг колонку в доме или таблицу — дороже, чем он стоит; отсутствие значения означает «отменять», как и требует §6.5 по умолчанию | `src/services/general-cleaning.ts` |
| P4-22 | Кому положено подтверждать и оценивать ротацию: §7 разводит эти действия, но прав под них не было | **Двумя правами: `rotation.confirm` и `rotation.score`.** Жилец подтверждает своё назначение — область «своё», чужое ему неотличимо от несуществующего. Оценку ставит только админ, и она вычищается из календаря на чтении, в одном месте: показывать её жильцу нельзя нигде, включая собственную | `src/lib/permissions.ts`, `src/services/rotation-calendar.ts` |
| P4-23 | Кому принадлежит фото уборки: чек принадлежит дому (P3-32), а снимок сделал жилец | **Проживанию исполнителя.** Файл дома жильцу не виден, и, приложив снимок, он тут же перестал бы его видеть. Через проживание видимость есть у обоих: у жильца — как у владельца, у админа — как у видящего дом. Ротация без исполнителя фото не принимает: прикладывать его не к кому | `src/services/files.ts` |
| P4-24 | Что делать с подтверждением отменённой ротации | **Отказ.** Отменённая уборка не состоялась и на рейтинг не влияет (§7); подтверждение вернуло бы её в жизнь мимо решения админа. Обратный путь есть и он явный: админ меняет статус занятия | `src/services/rotation-confirmation.ts` |
| P4-25 | До какой даты живёт долг по дополнительной ротации: §7 говорит «обнуляется 1 июля», но самой даты у записи не было | **`expires_at` считается той же функцией, что и конец договора** — `contractEndDate`: до 1 июля этого года, если пропуск был в первом полугодии, иначе следующего. Год рейтинга и год договора начинаются в один день, и разводить их двумя разными правилами значило бы завести второе первое июля | `src/services/rotation-close-day.ts` |
| P4-26 | Что происходит с самим занятием, когда его назначения закрыты как невыполненные | **Занятие тоже становится `missed`.** Иначе календарь показывал бы «Запланирована» у уборки, которая уже никогда не состоится, а статистика фазы считала бы её ожидающей. Обратный путь есть: админ правит статус задним числом (§7) | `src/services/rotation-close-day.ts` |
| P4-27 | Ключ идемпотентности автозакрытия дня | **Дата закрываемого дня, а не момент запуска.** Строка `job_runs` с ключом «вчера» не даёт закрыть тот же день дважды, даже если задание дёрнули руками или расписание сработало повторно (P3-18). Лишние запуски при этом безвредны — как и у месячных счетов | `src/services/rotation-close-day.ts` |
| P4-28 | На каком языке шапка и футер шаблона: колонки названы `header_i18n`, а текст пишет человек | **По локалям, но поле одно — текущей локали интерфейса.** Заставлять админа писать одно и то же трижды §6.7 не просит; при чтении берётся его язык, а если такого нет — первый заполненный. Так колонка используется по назначению и дом с двумя языками не ломается | `src/services/rotation-templates.ts` |
| P4-29 | Откуда берутся слова «сегодня ротаций нет» и «не назначен» в тексте для группы | **Из словаря интерфейса, параметрами расчётного ядра.** Ядро своих слов не знает: текст уходит людям, а язык дома знает интерфейс. Иначе в казахском доме сообщение приходило бы наполовину по-русски | `src/domain/rotation-template.ts` |
| P4-30 | В каком режиме календаря показывать текст для группы | **Только в дневном.** §6.7 привязывает кнопку к дню, и на неделе непонятно, какой день копировать. Шапка берётся по виду дня: если в нём есть генеральная уборка — её, иначе обычную | `src/app/(app)/rotations/page.tsx` |
| P4-31 | Каким правом закрыта статистика ротаций | **Правом на оценку, `rotation.score`.** Средняя оценка — это и есть оценки, а их §7 показывает только админу и суперадмину. Закрывать статистику правом на чтение календаря значило бы отдать жильцу то, что от него скрыто в самом календаре | `src/app/(app)/rotations/stats/page.tsx` |
| P4-32 | В каком порядке показывать людей, зоны и дни недели | **Сначала худшее среднее.** Списки читают сверху, а идут в них за проблемой: §7 и модуль 4 называют «худшие зоны» и «худшие дни» прямо. Строки без единой оценки уходят вниз — судить о них не по чему | `src/domain/rotation-stats.ts` |
| P4-33 | Что делать со статистикой отменённых ротаций и неоценённых выполненных | **Отменённые не считаются вовсе, неоценённые считаются как выполненные, но в среднее не входят.** Отменённая уборка не состоялась (§7), и её присутствие занижало бы и среднее, и долю пропусков. Выполненная без оценки — это не оценка «ноль»: админ просто не поставил её | `src/domain/rotation-stats.ts` |
| P4-34 | Где живёт приёмка фазы 4, если ряд у дома один | **В своих домах 6, 7 и 8 — по одному на ширину, и внутри файла сценарии идут последовательно.** Дома приёмки фазы 3 заняты её коммунальными периодами, а два сценария в одном доме собирали бы ряд друг поверх друга: второй видел бы в календаре чужие зоны. Сид вырос с пяти домов до восьми | `e2e/phase-4.spec.ts`, `src/db/seed.ts` |
| P4-35 | Что делает уборка прогона с ротациями удаляемых жильцов и зон | **Долг уходит вместе с человеком, назначение обезличивается.** Долг принадлежит человеку, а назначение — занятию: у него снимается исполнитель, как снимается автор у записи в журнале. Зоны прогона уносят с собой свои занятия, чек-листы, допуски и строки рядов — иначе внешние ключи не дают их убрать | `e2e/global-setup.ts` |
| P4-36 | Как жить с предзагрузкой ссылок, если после действия экран показывает снимок до правки | **Ссылки приложения идут через `@/components/ui/app-link` с выключенной предзагрузкой; прямой `next/link` в компонентах запрещён правилом ESLint с негативной фикстурой.** Отдельный флаг на каждой ссылке продержался бы до первой новой страницы. Все экраны здесь `force-dynamic`, и выигрыш предзагрузки не стоит показа устаревших данных | `src/components/ui/app-link.tsx`, `eslint.config.mjs` |
| P4-37 | В каком порядке отдавать доли коммунального периода | **По числу прожитых дней, затем по жильцу.** Порядок по времени создания не годился: все доли пишутся одной транзакцией и получают от `now()` одно время, после чего порядок оставался на усмотрение планировщика — тесты падали через раз. Порядок по дням ещё и осмыслен для того, кто список читает | `src/db/repositories/utilities.ts` |

## Решения фазы 5 (присутствие и рейтинг)

| № | Вопрос | Принято | Файлы |
|---|---|---|---|
| P5-1 | Что считать «пересечением порога сверху вниз»: §5.3 говорит о пересечении, а пример 5.2 срабатывает и на пороге, который в этом событии не пересекали | **Порог срабатывает, если он взведён и рейтинг оказался ниже него.** Прежнее значение в расчёте не участвует вовсе: память о прошлом — это и есть состояние порога, `armed`. Иначе пример 5.2 («31 → 25 задевает и порог 40, если он взведён») пришлось бы описывать отдельным исключением из правила | `src/domain/rating.ts` |
| P5-2 | Строгое ли неравенство у порогов вверх: §5.4 пишет «> 70» | **Строгое.** Ровно 70 предложения скидки не даёт, ровно 90 — тоже. Перезарядка симметрична: падение на уровень порога и ниже снова его взводит, поэтому «70 → 71 → 70 → 71» не выдаёт двух предложений подряд | `src/domain/rating.ts` |
| P5-3 | Границы рейтинга: жёсткие или накопительные | **Жёсткие 0 и 100 (инвариант 7).** Рейтинг не уходит в минус «под капотом»: иначе один тяжёлый месяц копил бы отрицательный запас, из которого человек не выбрался бы и безупречным поведением, а на экране всё это время стоял бы ноль | `src/domain/rating.ts` |
| P5-4 | Где хранится само значение рейтинга (вопрос 1 разбора фазы) | **Нигде: оно складывается из событий года.** Снимок разошёлся бы с историей при первой же правке события задним числом, а §5.6 обещает админу полную историю — значит она и есть источник истины. События года отбираются по `period_start`, и прошлые годы остаются читаемыми, не влияя на текущее число | `src/db/schema/rating.ts` |
| P5-5 | Как удержать одно правило на код, если уровень сети хранится пустым домом | **Двумя частичными уникальными индексами: по коду при пустом доме и по коду вместе с домом.** В PostgreSQL NULL не равен NULL, и обычная уникальность по трём колонкам пропустила бы сколько угодно правил сети с одним кодом — тест это и поймал | `src/db/schema/rating.ts`, `src/db/repositories/rating.ts` |
| P5-6 | Что удерживает от двойного начисления дельты за одну оценку | **Уникальность `(user_id, ref_type, ref_id)` у событий со ссылкой.** Пересчёт того же назначения не начислит дельту второй раз; действия админа ссылки не имеют и под ограничение не попадают — их вправе повторять | `src/db/schema/rating.ts` |
| P5-7 | Какой статус у краткосрочного отсутствия, если одобрение ему не требуется (§9) | **Сразу «одобрено», автор решения — сам жилец.** Держать его в очереди значило бы просить админа подтверждать то, на что он не влияет: §9 фиксирует опоздание фактом. В журнале при этом видно, что решение принял не админ | `src/services/absences.ts` |
| P5-8 | Кому показывать форму подачи отсутствия | **Тому, у кого есть проживание, а не просто право.** Админ дома живёт не в нём: сообщать о возвращении ему некуда, и форма для него не рисуется. Право при этом остаётся у роли — админ, живущий в доме, подаёт как все | `src/app/(app)/absences/page.tsx` |
| P5-9 | Обязательна ли причина отказа при отклонении отсутствия | **Обязательна.** §9 требует причину при подаче; отказ без объяснения оставил бы жильца без понимания, что исправить, и следующая заявка пришла бы такой же | `src/services/absences.ts` |
| P5-10 | От каких уборок освобождает отсутствие: §9 говорит «от ротаций общих зон», §6.4 и §6.5 про комнатные и генеральные молчат | **Только от обычных общих зон.** Комнатная уборка касается тех, кто живёт в комнате, генеральная — раз в месяц и всем домом: снимать их молча значило бы решать за админа то, что §6.3 оставляет ему — «отмени или назначь вручную» | `src/services/rotation-schedule.ts` |
| P5-11 | Когда одобренное отсутствие доходит до расписания | **В тот же момент, внутри транзакции решения.** Отложенный пересчёт означал бы, что задача админа появится только со следующей правкой расписания — то есть после пропущенной уборки. Отказ по той же причине возвращает человека в сетку | `src/services/absences.ts` |
| P5-12 | Что делать с уже закрытым периодом коммуналки, если отсутствие одобрили задним числом | **Ничего: закрытый период — снимок.** Он уже разнесён по счетам и попал в счета жильцов; пересчёт задним числом разошёлся бы с книгой проводок. Правка возможна только новым периодом или ручной корректировкой | `src/services/utilities.ts` |
| P5-13 | Что делать с событием рейтинга за уборку, оценённую задним числом (вопрос 2 разбора фазы) | **Событие одно на назначение, и переоценка правит его дельту.** Ограничение уникальности `(user_id, ref_type, ref_id)` превращает повтор в правку: второе событие начислило бы дельту дважды. Отмена занятия обнуляет дельту, а не удаляет строку — §5.6 обещает админу полную историю, и исчезнувшая уборка из неё выпала бы. Год события берётся от даты уборки, а не от дня правки | `src/services/rating.ts`, `src/db/repositories/rating.ts` |
| P5-14 | Видит ли жилец собственную историю событий | **Нет, только число.** §5.6 отдаёт ему «только число, без истории и детализации», а §7 прямо закрывает от него оценку уборки — из истории она читалась бы первой строкой. Право `rating.history` у жильца `none`, `rating.read` — `self` | `src/lib/permissions.ts`, `src/services/rating.ts` |
| P5-15 | Как правила из таблицы соотносятся со значениями §5.2 | **Накладываются по коду: умолчания, поверх — сеть, поверх — дом.** Замена таблицы целиком означала бы, что правка одной дельты стирает остальные, и пустая таблица оставила бы рейтинг без правил вовсе. Снятая галочка `is_active` убирает строку из набора — так удаляют правило, не удаляя историю | `src/services/rating.ts` |
| P5-16 | Что видит жилец, спросив рейтинг соседа | **«Не найдено», а не «нет прав» (P1-1).** Отказ по правам подтвердил бы, что такой человек в сети есть; чужое проживание жильцу невидимо, и вопрос обрывается на нём | `src/services/rating.ts` |
| P5-17 | Откуда у порога берётся строка правила, если §5.3 задаёт пороги текстом | **Недостающие пороги заводятся строками сети при первом срабатывании.** Состоянию порога и предложению скидки нужен `rule_id`: без строки не на что сослаться. Заводится только отсутствующее — правку суперадмина умолчание не возвращает | `src/services/rating.ts`, `src/db/repositories/rating.ts` |
| P5-18 | Из чего вычитается скидка за рейтинг | **Только из проживания (§5.4).** Коммуналка — доля в чужих расходах дома, штраф — наказание; уменьшать их за хороший рейтинг значило бы перекладывать разницу на соседей. Скидка режется до цены проживания, отрицательным оно не становится | `src/domain/monthly-invoice.ts` |
| P5-19 | Какие штрафы попадают в счёт месяца | **Начисленные до первого числа этого месяца (§3).** Штраф, выписанный после генерации, ждёт следующего счёта: иначе жилец узнавал бы о наказании из счёта, выставленного раньше самого штрафа | `src/services/monthly-invoices.ts`, `src/services/rating.ts` |
| P5-20 | Как отменить штраф, уже попавший в счёт | **Отдельной строкой сторно, а не правкой суммы.** Счёт жилец уже видел, и молчаливое изменение итога — это правка задним числом того, о чём ему сообщили. Отрицательная сумма разрешена ровно двум видам строк: скидке и сторно штрафа | `src/services/rating.ts`, `src/services/invoices.ts` |
| P5-21 | Что значит «выключить правило» на уровне дома и на уровне сети | **На доме — вернуться к сетевому, на сети — убрать правило вовсе.** Иначе «выключить» для дома означало бы «жить вообще без этого правила», чего §5.5 не даёт: дом переопределяет сеть, а не отменяет её. Выключенное сетевое правило — это способ убрать порог, не удаляя историю срабатываний | `src/services/rating.ts` |
| P5-22 | Что переносит «скопировать правила из дома…» | **Только переопределения дома-источника.** Копировать вместе с ними сетевые значило бы заморозить их в доме-приёмнике: будущая правка сети до него уже не дошла бы, хотя админ ждёт обратного | `src/services/rating-rules.ts` |
| P5-23 | Кто правит правила рейтинга | **Только суперадмин, и на сети, и на доме (§5.5).** Дельты и суммы штрафов — деньги и наказания всей сети; админ дома, правящий их у себя, назначал бы наказания сам себе | `src/lib/permissions.ts` |
| P5-24 | Как жилец узнаёт, что рейтинг скрыт, если права на настройки сети у него нет | **Флаг читается отдельной функцией репозитория без проверки прав.** В настройках сети секретов не хранится — это переключатели поведения; скрытому рейтингу число не уезжает на клиент вовсе, а не прячется разметкой | `src/db/repositories/settings.ts`, `src/services/rating-views.ts` |
| P5-25 | Что видит админ дома, у которого рейтинг жильцов скрыт от жильцов | **Всё то же самое: скрытие §5.6 касается только жильцов.** Админ и суперадмин видят число и историю всегда — иначе переключатель отключал бы разбор нарушений вместе с показом | `src/services/rating-views.ts` |
| P5-26 | Как «обнулить долги по доп. ротациям» 1 июля, не стирая историю | **Никак не стирать: у долга своя дата сгорания.** Долг заводится с `expires_at` на ближайшее 1 июля, и выборка берёт только не истёкшие — год закрывается сам, без переписывания строк, а история выполненного остаётся | `src/db/repositories/rotations.ts`, `src/services/rating-year.ts` |
| P5-27 | Что делает `rating-year-reset`, если рейтинг и так складывается из событий года | **Взводит пороги и оставляет отметку в истории.** Число сбрасывается само сменой года (P5-4), а вот снятый порог помнил бы падение прошлого года и молчал бы при новом. Отметка `year_reset` показывает админу границу года в истории | `src/services/rating-year.ts` |
| P5-28 | Что делать, если задание сброса запустили не 1 июля | **Ничего: прогон отклоняется.** Ручной запуск в ноябре открыл бы новый год посреди старого и стёр бы полгода порогов. Дата проверяется по календарю Алматы, как и всё остальное | `src/services/rating-year.ts` |
| P5-29 | Как приёмка проверяет попадание штрафа в счёт, если месячная генерация одна на сеть и на месяц | **Приёмка доводит цепочку до штрафа «ждёт счёта», а строку в счёте проверяет интеграционный тест.** Задание выставляет счета всей сети разом и один раз в месяц: три прогона приёмки на трёх ширинах не могут его делить, а подстраивать ручное выставление под тест значило бы проверять фикстуру | `e2e/phase-5.spec.ts`, `src/services/rating-thresholds.db-test.ts` |
| P5-30 | Какой дом видит суперадмин на экране рейтинга | **Тот, который выбрал сам.** Первый попавшийся дом сети — почти всегда не тот, ради которого он пришёл; выбор домов стоит рядом со списком, как в редакторе правил | `src/app/(app)/rating/page.tsx` |

## Решения фазы 6 (дэшборды, уведомления, PWA, инвентарь)

| № | Вопрос | Решение | Файл |
|---|---|---|---|
| P6-1 | Кто вправе читать чужие уведомления | **Никто: уведомление — личное сообщение.** Ни админ, ни суперадмин не открывают чужой центр уведомлений; о жильце они и так знают всё нужное из его данных. Чужой список приходит пустым, а не отказом в правах — иначе перебором адресатов читался бы состав сети (P1-1) | `src/db/repositories/notifications.ts` |
| P6-2 | Что удерживает очередь от повторной отправки | **Уникальность `(notification_id, channel)`.** Разбор идёт каждые пять минут, и повторная постановка того же уведомления для него норма: строка уже есть, второй раз она не заведётся | `src/db/schema/notifications.ts` |
| P6-3 | К кому привязывается подписка на push | **К тому, кто её заводит, а не к переданному адресату.** Адрес подписки уникален глобально: браузер выдаёт его сам. Иначе один жилец подписал бы свой браузер на уведомления другого | `src/db/repositories/notifications.ts` |
| P6-4 | Сколько попыток даёт очередь и с какой паузой | **Пять попыток, пауза — шаг задания разбора, пять минут.** Документация чисел не называет. Поля «когда пробовать снова» в модели данных нет, и заводить его ради экспоненциальной паузы значит менять модель: пауза выражена самим расписанием. Двадцать минут ожидания достаточно, чтобы отличить временную помеху от настоящей. Отдельно от счётчика попыток стоит окончательная ошибка канала: `410 Gone` от push-сервиса значит «адресата больше нет», и остаток попыток на неё не тратится | `src/domain/notifications.ts` |
| P6-5 | Что делать со строкой очереди, у которой нет канала | **Помечать `skipped` с именем канала в причине.** WhatsApp не подключён и, возможно, не будет; строка, ждущая отправителя, которого нет, копилась бы вечно и делала бы очередь нечитаемой. `skipped` — это честное «доставки не было и не будет», а не ошибка, и попытку оно не тратит | `src/services/notifications.ts` |
| P6-6 | Пишет ли разбор очереди строку в `job_runs` | **Нет: единственное задание без записи прогона.** Идемпотентность здесь держит не период, а сама строка очереди — доставленная больше не берётся, а параллельные прогоны разводит `for update skip locked`. Период в пять минут дал бы сто пять тысяч строк учёта в год и не добавил бы ни одной гарантии | `src/services/notifications.ts` |
| P6-7 | Какими каналами уходит уведомление по умолчанию | **Приложение всегда, push — только при живой подписке.** Уведомление в приложении и есть факт «человеку сообщили»: он не зависит от того, дошёл ли push. WhatsApp в набор по умолчанию не входит — канала нет, и ставить в очередь заведомо пропускаемое незачем; при необходимости вызывающий задаёт каналы явно | `src/domain/notifications.ts` |
| P6-8 | Кому можно адресовать уведомление | **Любому пользователю своей сети, мимо ролевой видимости отправителя.** Админ дома пишет суперадмину сети, а суперадмина в его списке нет и быть не должно. Из карточки адресата при этом ничего не раскрывается. Адресат чужой сети — «не найден», а не «нет прав» (P1-1) | `src/db/repositories/users.ts` |
| P6-9 | Как разбирается очередь на Vercel | **Внешним вызовом `/api/v1/cron/notifications-dispatch`, а не секцией `crons`.** На тарифе Hobby частота cron ограничена суточной: запись `*/5 * * * *` в `vercel.json` отклоняется платформой и роняет деплой целиком, вместе с уже работающими суточными заданиями. Это ровно тот случай, ради которого принят P1-5. В `vercel.crons.example.json` строка остаётся — она пригодится на платном тарифе | `vercel.json`, `docs/DEPLOY-VERCEL.md` |
| P6-10 | Как понимать ответ push-сервиса | **404 и 410 — подписки больше нет, 408, 429 и пятисотые — повторить, остальные четырёхсотые — окончательный отказ.** «Подписки нет» закрывает саму строку подписки: браузер её снял, и держать адрес незачем. Четырёхсотые, кроме этих, означают нашу ошибку — не тот ключ VAPID, слишком длинное тело, — и повтор её не исправит | `src/adapters/notify/webpush.ts` |
| P6-11 | Где живёт публичный ключ VAPID | **В окружении, отдаётся сервером при оформлении подписки.** Ключ не секрет, но и не константа сборки: `NEXT_PUBLIC_*` впекается в бандл, и смена ключа потребовала бы пересборки на всех окружениях. Приватный ключ остаётся секретом и в браузер не попадает | `src/adapters/notify/index.ts` |
| P6-12 | Что считать доставкой, если браузеров несколько | **Достаточно одного принявшего.** Подписки бывают на телефоне и на ноутбуке; получить уведомление дважды не страшно, не получить вовсе — страшно. Снятые подписки при этом отзываются, даже если доставка удалась на другой | `src/adapters/notify/webpush.ts` |
| P6-13 | Своя реализация Web Push или библиотека | **Своя, на WebCrypto.** Нужны ровно две операции — конверт `aes128gcm` (RFC 8291) и подписанный токен (RFC 8292), — и обе укладываются в стандартный API, который работает и в edge-рантайме. Проверяется тестом со стороны браузера: тест заводит пару подписчика и расшифровывает сообщение так же, как это делает service worker | `src/lib/crypto/webpush.ts` |
| P6-14 | Сколько живёт push на стороне сервиса | **Сутки (`TTL: 86400`).** Уведомления системы привязаны ко дню: напоминание о сегодняшней ротации, доставленное через неделю, дезинформирует. Сутки покрывают выключенный на ночь телефон и не переживают событие, о котором сообщают | `src/adapters/notify/webpush.ts` |
| P6-15 | Итог сплошной проверки класса I6 (доступ по идентификатору) | **Одна дыра на весь код: состояния порогов рейтинга.** Проверены все запросы репозиториев, где строка берётся по идентификатору. Общий рабочий приём оказался верным: функция без контекста вызывается только после того, как её родитель — счёт, период, ущерб, назначение — получен запросом с контекстом, и чужой идентификатор отсекается там. Исключением были `readThresholdStates` и `writeThresholdStates`: они принимали контекст и явно его игнорировали (`void context`), а таблица `rating_threshold_states` не имеет `org_id`. Сеть у состояний всё же есть — та, в которой числится жилец, — и теперь она проверяется через него. Негативная фикстура: `пороги жильца чужой сети не читаются и не пишутся` | `src/db/repositories/rating.ts` |
| P6-16 | Правило устойчивого порядка списков | **Последний ключ любой сортировки в репозитории — идентификатор строки.** Строки, записанные одной транзакцией, получают от `now()` одно и то же время, и сортировка по `created_at` перестаёт их различать: порядок остаётся на усмотрение планировщика. Так уже ломались список аккаунтов (I5) и раздача генеральной уборки. Проверка сплошная — двадцать три сортировки, все дополнены идентификатором: строки счёта, движения депозита, доли ущерба, проводки и их строки, документы, журнал аудита, дома, группы допуска, места, зоны, слоты рядов, строки коммуналки, доли периода. Правило исполняемое: тест разбирает исходники репозиториев и падает на сортировке без уникального ключа | `src/db/repositories/ordering.test.ts` |
| P6-17 | Как суперадмин ведёт дом без админа | **Тем же выбором дома, что и на остальных экранах.** Права у него на это были всегда — область `org` покрывает всё, что делает админ, — а интерфейс дом брал только из учётной записи. Календарь ротаций поэтому показывал суперадмину пустоту, а экран отсутствий — первый дом сети, где нашлись проживания, то есть почти всегда не тот. Оба получили список домов сверху и выбор в адресе, как счета и коммуналка. Расчётная часть покрыта тестом: в доме без админа суперадмин заводит ряд, генерирует расписание, ставит оценку, закрывает коммуналку и выставляет счёт | `src/app/(app)/rotations/page.tsx`, `src/services/house-without-admin.db-test.ts` |
| P6-18 | Что считать непрочитанным | **Записи в приложении, у которых не проставлено `read_at`.** Счётчик по каналам доставки был бы неверен дважды: push система уже показала, и второй раз он не новость, а строка очереди `skipped` вообще не была доставкой. Непрочитанное — это то, что человек не открывал, а не то, что не ушло по проводам | `src/app/(app)/layout.tsx` |
| P6-19 | Видит ли жилец уведомления после переезда в другой дом | **Да: уведомление принадлежит человеку, а не дому.** «Счёт выставлен» и «уборка не подтверждена» остаются его историей и после переезда — адрес был у события, а не у сообщения. Границей остаётся сеть: список фильтруется по `org_id` и адресату, как и всё остальное | `src/db/repositories/notifications.ts` |
| P6-20 | Как показывать код события в интерфейсе | **Словарём по закрытому списку кодов, с общим заголовком для неизвестного.** Точка в коде (`rotation.reminder`) у next-intl означает вложенность, поэтому в словаре ключ пишется слитно (`rotationReminder`), а перевод делает чистая функция. Код, которого в списке нет, показывается как «Уведомление»: экран не должен выводить сырой машинный код, но и терять сообщение из-за незнакомого типа тоже не должен | `src/domain/notifications.ts` |
| P6-21 | Как различаются два прогона напоминаний в сутки | **Ключом прогона: дата и слот, `2026-09-07:morning`.** Задание идёт в 09:00 и 19:00, и общий ключ по дате сделал бы вечерний прогон повтором утреннего. Слот выводится из часа запуска — до полудня утренний, после вечерний, — а не из аргумента: расписание может опоздать, но не может перепутать день с вечером | `src/services/rotation-reminders.ts` |
| P6-22 | Сколько раз сообщать о просрочке возврата депозита | **Один раз, в первый день после срока.** Ежедневное «просрочено» превращается в шум, который перестают читать, а сам долг и так виден на экране суперадмина постоянно. До срока предупреждения идут за 7, 3 и 1 день, как в модуле 1 | `src/services/expiry-reminders.ts` |
| P6-23 | Откуда задания берут тексты уведомлений | **Из тех же словарей `messages/*.json`, что и интерфейс.** Уведомление хранит три локали, и писать их строками в коде задания значило бы завести вторую, невидимую систему переводов. Названия, которые сами живут на трёх языках — тип справки, дом, — подставляются переводом в каждую локаль, а не одной строкой | `src/lib/i18n/notification-texts.ts` |
| P6-24 | Кому уходит уведомление о деле дома | **Админам дома, а если админа нет — суперадмину сети.** Дом без админа ведёт сеть (P6-17), и список к отбою или напоминание о коммуналке не должны пропадать вместе с отсутствующим адресатом | `src/services/job-actor.ts` |
| P6-25 | На каком языке манифест установки | **На языке сети по умолчанию.** Манифест у приложения один, а язык — атрибут пользователя (P0-2), и система читает манифест до входа, когда о человеке ещё ничего не известно. Брать язык запроса значило бы, что имя значка на домашнем экране зависит от того, кто последним открыл страницу | `src/app/manifest.ts` |
| P6-26 | Что кеширует service worker | **Только оболочку: страницу обрыва связи и иконки.** Места, счета и ротации меняются каждый день; показать вчерашний список хуже, чем честно сказать «нет сети». Перехватываются только переходы по страницам — запрос к API в офлайне обязан вернуть ошибку, иначе клиент примет HTML-заглушку за ответ | `public/sw.js` |
| P6-27 | На каком языке страница обрыва связи | **На всех трёх сразу.** Её отдаёт service worker, когда сети нет, и до словарей интерфейса он не дотягивается: язык пользователя ему неизвестен. Три коротких строки подряд — как объявление на двери; выбирать за человека язык, которого он может не знать, здесь не из чего | `public/offline.html` |
| P6-28 | Откуда берутся иконки приложения | **Рисуются кодом `scripts/make-icons.mjs`.** Знак простой — синий квадрат и жёлтый дом фирменных цветов, — и хранить ради него бинарный файл, который никто в репозитории не может пересобрать, незачем. Зависимостей генератор не требует: PNG собирается вручную, сжатие даёт `node:zlib`. Тест проверяет, что файлы на месте и заявленного размера — без иконок браузер просто не предложит установку | `scripts/make-icons.mjs`, `scripts/icons.test.ts` |
| P6-29 | Почему файлы установки не проходят проверку сессии | **Браузер просит их без cookie, и редирект на вход отдавал бы страницу вместо файла.** Манифест, service worker, иконки и страница обрыва связи исключены из `matcher` middleware. Это не ослабление модели безопасности: всё перечисленное лежит в `public/` и публично по определению, а данных в нём нет. До правки установка молча не работала — вместо JSON манифеста и картинок приходил HTML экрана входа, и заметить это можно было только на телефоне | `src/middleware.ts` |
| P6-30 | Какую уборку показывать на дэшборде жильца | **Вчерашнюю неподтверждённую, если она есть; иначе ближайшую будущую.** Вчерашнюю ещё можно закрыть сегодня — до 23:55, когда автозакрытие отметит её невыполненной (§7). Завтрашняя подождёт, а вчерашняя — нет | `src/services/dashboard.ts` |
| P6-31 | Что попадает в блок «Требуется внимание» | **Незагруженный обязательный документ, отклонённый, просроченный и истекающий в ближайшие тридцать дней, плюс незакрытые шаги заселения.** Тридцать дней — тот же срок, с которого предупреждает задание `documents-expiry`: экран и напоминание не должны расходиться в том, что считать срочным | `src/services/dashboard.ts` |
| P6-32 | Подтверждение уборки прямо с дэшборда | **Кнопка без фото, рядом — ссылка в календарь.** Фото и комментарий живут на карточке занятия, и переносить их на дэшборд значило бы держать две формы одного действия. Кнопка появляется только в те два дня, когда подтверждение вообще принимается | `src/app/(app)/resident-dashboard.tsx` |
| P6-33 | Что показывать в «переоткрытых периодах» суперадмина | **Все незакрытые периоды прошедших месяцев.** Переоткрытый период по данным неотличим от просто незакрытого: статус у обоих `draft`, а сам факт переоткрытия живёт в журнале аудита. Решения требуют оба случая одинаково — деньги за месяц не разнесены, — поэтому разделять их на экране незачем | `src/services/dashboard.ts` |
| P6-34 | Что считать «спорным штрафом» | **Штраф в статусе `pending`.** Отдельного «спорного» статуса в модели нет: штраф либо ещё не попал в счёт (`pending`), либо применён, либо отменён. Отменить можно только первый — он и ждёт решения | `src/services/dashboard.ts` |
| P6-35 | Сеть таблицей или строками | **Строками.** Колонок шесть — дом, места, выставлено, оплачено, рейтинг, оценка уборок, — и таблица на 375px потребовала бы горизонтальной прокрутки, которой в системе нет (docs/05-DESIGN-SYSTEM.md) | `src/app/(app)/network-dashboard.tsx` |
| P6-36 | Как считать дробные количества инвентаря | **Целым числом сотых долей, а строка `numeric(12,2)` — только формат хранения.** Правило целых тенге сюда не переносится дословно: у инвентаря своя единица, и полтора литра краски существуют. Но считать дробное в `number` нельзя по той же причине, по какой нельзя деньги — `0.1 + 0.2` не даёт `0.3`, и на третьем перемещении это стало бы видно | `src/domain/inventory.ts` |
| P6-37 | Права на инвентарь | **Свои действия `inventory.read` и `inventory.manage`, у админа — область «дом».** Бухгалтерия (`accounting.*`) осталась делом суперадмина, а инвентарь ведёт дом: подвешивать его к книге проводок значило бы либо закрыть админу свой склад, либо открыть ему чужие проводки | `src/lib/permissions.ts` |
| P6-38 | Можно ли править количество позиции руками | **Нет: количество — следствие движений.** Приход прибавляет, расход и списание вычитают, инвентаризация корректирует. Правка остатка мимо истории оставила бы число, которое ничем не объясняется. Перемещение количество не меняет — позиция переезжает целиком; дробить её на два дома значит завести вторую позицию | `src/services/inventory.ts` |
| P6-39 | Как выгружать списки в CSV и XLSX | **Своим кодом, без библиотеки.** CSV — точка с запятой и метка порядка байтов: в русской и казахской локали Excel ждёт именно этот разделитель, а без метки читает UTF-8 как однобайтовую кодировку. XLSX — zip из пяти небольших XML, собранный вручную: формат используется в самом простом виде (строки и числа, без формул и стилей), и тянуть ради него чужую сборку незачем. Архив проверяется тестом на структуру и разбирается обратно | `src/lib/export/` |
| P6-40 | Как выгружается дробное количество | **Строкой, как хранится.** `12.50` — это ровно две сотых доли; превращение в число `12.5` теряет заявленную точность, а выгрузку читают глазами и сверяют, а не пересчитывают | `src/services/inventory-audit.ts` |
| P6-41 | Что делает закрытие ведомости с непроверенной строкой | **Ничего.** Пустое «по факту» — это «не считали», а не «ноль»: обнулять по нему остаток значило бы списать всё, до чего не дошли руки. Расхождения остальных строк становятся движениями `audit_adjust` со ссылкой на ведомость | `src/services/inventory-audit.ts` |
| P6-42 | Почему шаг приёмки с заданием идёт на одной ширине | **Задание рассылает по всей сети сразу и идемпотентно по паре «день и слот».** Три копии приёмки, идущие параллельно на трёх ширинах, в одном слоте физически не могут разослать трижды: второй и третьей задание честно ответит «уже разослано». Это свойство системы, а не теста, и притворяться, что его нет, приёмка не должна. Дома 9, 10 и 11 остаются по одному на ширину — подготовку каждая делает в своём, — а экраны уведомлений проверяются на всех трёх шириной `notifications.spec` и приёмкой установки | `e2e/phase-6.spec.ts` |
| P6-43 | Как приёмка переживает собственную идемпотентность | **Прогон снимает записи `job_runs` заданий фазы 6 перед стартом.** Слот, отработанный вчерашним прогоном, не разослал бы ничего сегодняшнему, и приёмка проходила бы один раз в сутки. Это фикстура прогона, а не послабление правила: сама идемпотентность проверяется внутри приёмки повторным вызовом того же задания | `e2e/global-setup.ts` |

## Решения фазы 7 (API, приёмка, документация)

| № | Вопрос | Решение | Файл |
|---|---|---|---|
| P7-1 | Чем хешируется токен API | **SHA-256 без соли, а не argon2.** Медленный хеш защищает от подбора по словарю — так придумывают пароли люди. Токен выдаёт система: тридцать два случайных байта не подбираются вовсе, а argon2 пришлось бы считать на каждом запросе бота. Соли нет по той же причине: одинаковых токенов не бывает, и радужной таблицы для такого пространства не существует. Значение показывается один раз, в базе только хеш | `src/lib/crypto/api-token.ts` |
| P7-2 | Что означает скоуп рядом с ролью | **Скоуп сужает права выдавшего и никогда не расширяет.** У каждого скоупа есть действие матрицы прав, и при выдаче оно проверяется правом человека: выдать токен на то, чего у него нет, нельзя — иначе выдача стала бы способом обойти собственную роль. Поэтому и токены заводит только суперадмин | `src/domain/api-scopes.ts` |
| P7-3 | Сколько живёт токен без явного срока | **Год.** В модели `expires_at` необязателен, но бессрочный токен — это ключ, который никто никогда не пересмотрит. Год заставляет вернуться к вопросу и не мешает работе бота; явный срок при выдаче остаётся возможным | `src/services/api-tokens.ts` |
| P7-4 | Чем проверяется скоуп уведомлений | **Правом видеть жильцов.** Собственного действия у уведомлений в матрице нет, и заводить его не нужно: право писать человеку всегда следовало из права его видеть | `src/domain/api-scopes.ts` |
| P7-5 | Чью роль носит токен | **Роль выдавшего, взятую в момент запроса.** Собственной роли у токена нет: он действует от имени человека, и понижение его роли или архивация учётной записи сразу отражаются на боте. Иначе выданный ключ пережил бы увольнение. Дом токена при этом сужает область до одного дома, даже если у выдавшего домов больше | `src/lib/api/token-auth.ts` |
| P7-6 | По чему считается частота запросов бота | **По самому токену, не по адресу.** Боты ходят из одного облака, и общий счётчик по IP закрывал бы одного из-за другого. Порог — сто двадцать запросов в минуту (docs/06-API.md), хранилище то же, что у входа по телефону | `src/lib/api/token-auth.ts` |
| P7-7 | Что отвечать на отозванный и просроченный токен | **То же, что на несуществующий: «не авторизован».** Разница наружу не выдаётся — иначе перебором значений выяснялось бы, какие из них когда-то были настоящими. Внутри разница видна по журналу | `src/lib/api/token-auth.ts` |
| P7-8 | Две проверки на каждый запрос бота | **Роль и скоуп проверяются отдельно.** Роль отвечает на вопрос «вправе ли этот человек», скоуп — «разрешено ли это боту, которому он выдал ключ». У входа по сессии скоупов нет вовсе: человек ограничен ролью, и требовать от него скоуп было бы бессмыслицей | `src/lib/api/access.ts` |
| P7-9 | Что не отдаётся боту вместе с ротациями и местами | **Оценки уборок и жильцы.** Оценку видит только админ (§7), и через токен она не открывается никому; в ответе о местах есть «занято» или «свободно», но не имя занявшего — это другой скоуп и другой маршрут | `src/app/api/v1/rotations/route.ts` |
| P7-10 | Чем собирается OpenAPI | **Средствами самого zod.** `docs/06-API.md` называет `zod-to-openapi`, но в zod 4 появился `z.toJSONSchema`, и отдельная библиотека стала лишней зависимостью ради одной функции. Схемы остаются на zod — источник правды один | `src/lib/api/openapi.ts` |
| P7-11 | Как отдаётся Swagger UI | **Страницей, которая полезна и без него.** Сам Swagger UI подключается с CDN, но список маршрутов отрисован обычным HTML сразу: Docker-установка без выхода в интернет возможна, и пустой экран с крутящимся колесом объяснял бы меньше, чем простая таблица. Тянуть три мегабайта статики в сборку ради служебного экрана не стоит | `src/app/api/docs/route.ts` |
| P7-12 | Что не попадает в спецификацию | **Задания планировщика и сама спецификация.** Задания не часть API для ботов: они защищены отдельным секретом и вызываются расписанием, а документ, который их перечисляет, приглашал бы дёрнуть их руками. Список сверяется тестом в обе стороны: маршрут без описания и описание без маршрута роняют прогон | `src/lib/api/openapi.test.ts` |
| P7-13 | Сколько домов наполняет сид | **Пять из одиннадцати, как и говорит роадмап.** Остальные шесть остаются каркасом: они отданы приёмкам, и сидовые жильцы в них ломали бы прогонам счётчики и списки. Прогон приёмок вызывает сид с выключенным наполнением — ему нужны только дома и учётные записи | `src/db/seed-content.ts` |
| P7-14 | Где материализуется расписание сида | **В `seed.cli.ts`, а не в самом сиде.** Генерация занятий — это сервис с проверкой прав, а `src/db` о сервисах ничего не знает и знать не должен: обратная зависимость перевернула бы слои. CLI — верхний уровень, ему доступно и то и другое | `src/db/seed.cli.ts` |
| P7-15 | Формат телефонов админов в сиде | **Номер дома дополняется нулями до одиннадцати цифр.** Простая склейка давала с десятого дома `+770100000010` — на две цифры длиннее настоящего казахстанского номера. У домов с первого по девятый номера не изменились | `src/db/seed.ts` |
| P7-16 | Как проверяется версия схемы при старте | **Списком миграций, уехавшим в сборку, против записей в `drizzle.__drizzle_migrations`.** Папку с миграциями приложение во время работы не видит — в standalone-сборке её рядом нет, — поэтому список кладётся в исходник скриптом при генерации. База впереди кода ошибкой не считается: так выглядит выкатка, где миграции применены раньше обновления экземпляров. Обратное — ошибка (указание владельца, `docs/DEPLOY-VERCEL.md` §10) | `src/db/schema-version.ts` |
| P7-17 | Что делает приложение на отставшей схеме | **Падает понятной ошибкой при первом обращении к данным.** Половина работающих запросов и половина падающих на неизвестной колонке — худшее из состояний: человек видит случайные ошибки на случайных экранах и не понимает причины. Проверка идёт один раз на процесс, в защищённой зоне и при разборе актёра REST; спецификация и страница документации базы не касаются и падать вместе с ней не должны | `src/lib/api/route.ts`, `src/app/(app)/layout.tsx` |
| P7-18 | Где выдаются токены | **На экране настроек сети, у суперадмина.** Сервис выдачи появился раньше экрана, и без него функция была бы недоступна людям — а приёмка не имеет права ходить в обход интерфейса. Значение показывается один раз, сразу после выдачи: в базе только хеш, и показать снова неоткуда | `src/app/(app)/settings/api-tokens/page.tsx` |
| P7-19 | Сколько домов заводит сид | **Пять, как в сид-данных роадмапа; число — параметр.** Прогон приёмок просит одиннадцать: дома с третьего по одиннадцатый отданы приёмкам фаз 3–7, по одному на ширину. Живой установке лишние дома незачем — их заводит владелец. Приёмка фазы 3 упала ровно на этом: сидовые жильцы попали в её дом и разделили с ней коммуналку | `src/db/seed.ts` |
| P7-20 | Откуда берётся корневая папка Drive | **Драйвер заводит её сам, если `GDRIVE_ROOT_FOLDER_ID` не задан.** Область `drive.file` показывает приложению только созданные им объекты: папка, заведённая владельцем в браузере, отвечает `404`, и прежний шаг 4 инструкции `docs/GDRIVE-SETUP.md` требовал невозможного (дефект нашёл владелец). Драйвер ищет «Nice Almaty» в «Моём диске», создаёт её при первом обращении и один раз за процесс сообщает идентификатор в журнал — владельцу, чтобы тот положил его в окружение. Поиск идёт одним обещанием на процесс: параллельные загрузки не должны завести две папки. Путь чтения папку не создаёт — на пустом диске `exists` отвечает «нет», а не заводит папку на каждый промах | `src/adapters/storage/gdrive.ts` |
| P7-21 | Как вернуть типы документов, шаблон договора и счета сети на живую базу | **Сид в режиме скелета: `pnpm db:seed --skeleton`** — организация, суперадмин и эти три сущности, ноль домов и ноль жильцов. Экранов у них нет (модули 10 и 11), заводит их только сид, а полный сид на живой базе вернул бы пять демо-домов с жильцами. Неизвестный аргумент останавливает сид: молча проигнорированный флаг — это полный сид там, где просили скелет. Флаг проходит через стража `db:*` как есть, рядом с `--allow-remote` | `src/db/seed-options.ts`, `src/db/seed.cli.ts` |

## Решения фазы 8 (настройки сети)

| № | Вопрос | Решение | Файл |
|---|---|---|---|
| P8-1 | Формат номера договора: в ТЗ его нет вовсе | **«ГГГГ-НННН»: год, дефис, порядковый номер года с ведущими нулями.** Нумерация сквозная в пределах сети и начинается заново каждый год — так номера договоров и читают. Номер присваивает система при заведении проживания: вводимый руками рано или поздно повторится, а договор с чужим номером — это спор, а не опечатка. Уникальность держит индекс по сети; за пределами четырёх знаков номер просто становится длиннее, и поиск последнего сортирует сперва по длине — иначе «2026-10000» оказался бы меньше «2026-9999» | `src/domain/contract-number.ts` |
| P8-2 | Что делать с проживаниями, заведёнными до нумерации | **Номер выдаётся при первой сборке договора.** Задним числом ничего не переписывается: у кого номер есть, тот его и сохраняет. Миграция ничего не заполняет — на боевой базе проживаний нет, а на демо-данных выдуманные номера были бы хуже пустых | `src/services/contract-numbers.ts` |
| P8-3 | Шифровать ли орган выдачи удостоверения | **Нет.** Шифруются ИИН и номер удостоверения — они опознают человека. Орган выдачи не опознаёт никого и печатается в договоре как есть; шифрование добавило бы расшифровку на каждую сборку договора и запись в журнал раскрытий там, где раскрывать нечего | `src/db/schema/resident-profiles.ts` |
| P8-4 | Кому доступен план счетов и какие счета заводятся руками | **Суперадмину; руками заводятся только касса, Kaspi и общий счёт.** Деньги всей сети — не дело одного дома, а журнал проводок админ по-прежнему видит на своём экране учёта. Депозитный и коммунальный фонды появляются вместе с сетью, фонд дома — вместе с домом (`createHouse`): заводить их руками значило бы позволить сети остаться с двумя депозитными фондами. Системные счета не архивируются вовсе — на них стоят типовые проводки | `src/services/chart-of-accounts.ts` |
| P8-5 | Что делает прогон приёмок с типами документов и счетами, которые он завёл | **Убирает за собой по префиксу `probe_`.** Интерфейс их не удаляет — там только архивация, — и от прогона к прогону экраны настроек росли бы, а интеграционный тест скелета сети считал бы чужие строки. Ровно на этом он и упал в первый же прогон после T8.3: проверки стали смотреть вхождение своих строк, а не общий счёт таблицы (инцидент I7 повторился в новом месте) | `e2e/global-setup.ts` |
| P8-6 | Как приёмка фазы обходится с общими на сеть сущностями | **Просмотр — на всех трёх ширинах, правки — на одной.** Шаблон договора в сети один, и три копии приёмки, правящие его одновременно, ловили бы чужие версии: точно так же в фазе 6 задание рассылки идёт на одной ширине (P6-42). Типы документов и счета общие тоже, но у них код свой у каждой ширины — как дом в приёмках фаз 3–7. Жилец приёмки заводится в доме 9, 10 или 11 | `e2e/phase-8.spec.ts` |
| P8-7 | Чем разводить одновременные заселения за номером договора | **Советующей блокировкой на время транзакции (`pg_advisory_xact_lock`), а не последовательностью.** Последовательность PostgreSQL не откатывается вместе с транзакцией и оставила бы дыры в нумерации договоров — в документе, который читает человек и подписывает юрист, пропущенный номер объясняется хуже, чем очередь в полсекунды. Блокировка не трогает таблицу, живёт до конца транзакции и снимается сама; уникальный индекс остаётся последним рубежом | `src/services/contract-numbers.ts` |

## Решения фазы 9 (первый прогон на боевой)

### I9 — разбор: очистка стёрла скелет сети (8 сентября 2026)

Строка таблицы выше — короткий итог. Здесь разбор целиком: что проверено,
что снято и что нужно снять с боевой базы, чтобы закрыть вопрос.

#### Что случилось

На боевой базе после очистки обнулились `accounts`, `document_types`
и `contract_templates` — вместо 5/3/1 нули. Организация и суперадмин уцелели,
дома и жильцы ушли как задумано.

#### Почему — пока неизвестно. Прежний ответ снят

Первое объяснение — список сохраняемых таблиц потерял хвост при переносе — снято:
владелец запускал полный список одной строкой, и `DELETE 0` в выводе не было. Причина не найдена, вопрос открыт, и ниже написано ровно то,
что проверено, а не то, что похоже на правду.

Проверено после ответа владельца, на локальном PostgreSQL 16 со схемой из тех же
девятнадцати миграций и полным сидом:

- скрипт с полным списком счета, типы документов и шаблон не трогает: после
  прогона 5/3/1 на месте. `NOTICE` печатает список из 47 таблиц — ни одного
  из шести сохраняемых имён в нём нет;
- `truncate` не может увести строки из таблицы, которой нет в списке: он
  затрагивает только перечисленные и их потомков по наследованию, а наследования
  в схеме нет. `cascade` в скрипте не используется;
- каскадных удалений в схеме нет вовсе: все внешние ключи объявлены
  `on delete no action` — поэтому `delete from houses` не мог утянуть счета,
  а `delete from users` — типы документов;
- шаг `delete from accounts where house_id is not null` оставляет счета сети:
  у них `house_id` пуст.

Отсюда следует, что либо на боевой базе выполнялся не тот текст, что лежит
в `cleanup.sql`, либо этих строк там не было ещё до очистки. Различить эти два
случая по коду нельзя — нужна сама боевая база.

#### Три запроса, которые закрывают вопрос (все только читают, выполняет владелец)

Первый: были ли строки вообще. Счётчик вставок накопительный, `truncate`
его не сбрасывает:

```sql
select relname, n_tup_ins, n_tup_del, n_live_tup
  from pg_stat_user_tables
 where relname in ('accounts', 'document_types', 'contract_templates')
 order by relname;
```

- `n_tup_ins = 0` — строк не было никогда. Тогда очистка ни при чём: сид
  на боевой базе выполнялся сборкой, в которой этих таблиц ещё не было
  (счета, типы документов и шаблон появились в фазах 2 и 3), а дома
  с их фондами владелец заводил через интерфейс — этим объясняется и отсутствие
  `DELETE 0`, потому что фонды домов удалялись настоящими строками.
- `n_tup_ins` больше нуля при `n_live_tup = 0` — строки были и стёрты.
  `n_tup_del = 0` рядом означает, что стёр их `truncate`, а не `delete`.

Второй, если строки всё-таки были: точный текст выполненного `truncate`.
На Supabase `pg_stat_statements` включён по умолчанию и пишет в том числе
служебные команды:

```sql
select calls, query
  from pg_stat_statements
 where query ilike '%truncate%'
 order by calls desc
 limit 20;
```

В строке будет виден список таблиц ровно таким, каким его получил сервер.
Если в нём есть `public.accounts`, `public.document_types`
или `public.contract_templates` — до сервера дошёл не тот текст, что в файле,
и дальше вопрос только в том, где он изменился. Если их там нет, а строки
пропали — причина не в очистке, и искать надо в другом месте.

То же самое, но человеческим экраном: **Advisors → Query Performance**
в дашборде Supabase, и **History** в SQL Editor, где хранятся запущенные
из него запросы.

#### Что сделано, пока причина не найдена

Скрипт теперь защищён от результата, а не от версии причины: перед `truncate`
он запоминает количество строк в шести сохраняемых таблицах, а после `truncate`
сверяет. Если хоть одна похудела — исключение, транзакция откатывается целиком,
база остаётся нетронутой. Что именно увело строки — урезанный список, каскад,
триггер или что-то ещё, чего никто не предвидел, — для этой проверки неважно.

Проверено на живой базе негативной фикстурой: в список очистки силой добавлен
`document_types`, прогон оборвался сообщением «Очистка задела скелет сети
(document_types: было 3, стало 0). Транзакция откачена», код возврата 3,
база осталась полной — 5 домов, 46 записей, 40 проживаний.

Перед `commit` добавлена вторая проверка: если после очистки в сети нет ни типов
документов, ни шаблона, ни счетов сети, ни учётных записей — тоже отказ
и откат, с подсказкой сначала восстановить скелет. Прежние проверки списка
(длина и существование таблиц) оставлены как были.

Восстановление скелета сети после такой очистки — `docs/DEPLOY-VERCEL.md` §11.

### I11 — разбор: прямая загрузка в Drive из браузера (9 сентября 2026)

**Что проверено.**

- Поток по коду: `POST /api/v1/files/upload-session` открывает у Drive resumable
  session (`src/adapters/storage/gdrive.ts`, `createUploadTarget`) и отдаёт клиенту
  её адрес `https://www.googleapis.com/upload/drive/v3/files?uploadType=resumable&upload_id=…`;
  клиент шлёт туда `PUT` с `content-type` файла (`document-cards.tsx`,
  `receipt-upload.tsx`, `rotation-photo-upload.tsx`, `contract-view.tsx`);
  затем `POST …/complete`. `PUT` — межсайтовый запрос с непростым заголовком,
  браузер сначала шлёт preflight `OPTIONS` и требует `Access-Control-Allow-Origin`
  в обоих ответах.
- Смысл ошибки: `Failed to fetch` — это `TypeError` из `fetch`, браузер не получил
  читаемого ответа. Отказ Google со статусом и CORS-заголовками выглядел бы иначе:
  сработала бы ветка `!sent.ok`, на экране был бы ключ `files.errors.upload`,
  а в консоли — статус и тело. Значит, ответ от страницы скрыт: CORS-блок
  либо сетевой обрыв.
- Документация Google Cloud Storage, «Initiate a resumable upload session»
  (сервер загрузки `…/upload/…` у Storage и Drive общий): «If you have enabled
  Cross-Origin Resource Sharing, you should also include an Origin header in both
  this and subsequent upload requests». Драйвер открывал сессию без `Origin`.
  Документация Drive о CORS молчит; в обсуждениях клиентских библиотек Google
  (googleapis/google-cloud-dotnet #2755, #5715) описан ровно этот случай: сессия
  открыта сервером, `PUT` из браузера падает без `Access-Control-Allow-Origin`.
- Версии, отсечённые по коду. CSP: `connect-src` не задан нигде — ни в
  `next.config.ts`, ни в middleware. Service worker (`public/sw.js`): перехватывает
  только `mode === 'navigate'`, `PUT` не трогает. Рантайм: у роутов `/api/v1` нет
  `runtime = 'edge'`, Node-овский `fetch` (undici, Node 24) заданный вручную
  `Origin` передаёт — проверено скриптом с локальным HTTP-сервером.

**Что проверить нельзя.** Живой Drive: ключей OAuth у разработки нет. Не подтверждено,
что после правки Google отвечает `Access-Control-Allow-Origin` на preflight и на `PUT`
для домена боевой. Это единственное звено, которое остаётся на слово документации.

**Как владельцу различить версии в браузере.** DevTools → Network, фильтр `googleapis`,
загрузить любой документ.

1. *CORS без `Origin`* (принятая версия). До правки: строка `OPTIONS` или `PUT`
   к `upload/drive/v3/files?…upload_id=…` со статусом `CORS error`
   (в Chrome — `(blocked:cors)`), в консоли «has been blocked by CORS policy:
   No 'Access-Control-Allow-Origin' header is present on the requested resource».
   После правки: `OPTIONS` 200 с `Access-Control-Allow-Origin: https://<домен боевой>`,
   `PUT` 200 с JSON `{"id": …}`, затем `complete` 200 и файл в статусе `ready`.
   Если после правки консоль по-прежнему говорит о CORS — версия ложная,
   разбор возвращается к началу; нужен текст заголовков ответа `OPTIONS`.
2. *Google отвергает сессию* (размер или тип не сошлись с объявленными,
   сессия истекла). Ответ был бы виден: статус 4xx в столбце Status, текст в Preview,
   на экране `files.errors.upload`, а не `Failed to fetch`. По описанию владельца
   этого не было.
3. *Блокировщик или расширение браузера*: статус `(blocked:other)` или
   `net::ERR_BLOCKED_BY_CLIENT`; в окне инкогнито без расширений загрузка проходит.
4. *Сеть*: `net::ERR_CONNECTION_RESET`, `ERR_NAME_NOT_RESOLVED`; на другом
   подключении не повторяется.
