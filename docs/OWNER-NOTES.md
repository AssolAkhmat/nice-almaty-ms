**Что ломает.** Три вещи, каждая проверяемая:

- Навигация и дэшборд админа строятся по правам: со снятым полномочием пункты

  зависеть от данных. Кешировать запреты дольше запроса нельзя — снятое право
  должно действовать сразу, а не после перелогина.
- Контекст в тестах собирается руками в десятках файлов. Поле необязательное,
  поэтому старые тесты не сломаются, но каждый новый запрет требует своей
  фикстуры — иначе правило снова окажется мёртвым.

## 1. Миграции против Supabase

Строка для миграций — прямое подключение или **сессионный** пулер, порт 5432.
Транзакционный пулер (6543) не годится: `drizzle-kit` выполняет DDL, а в режиме
transaction pooling ни DDL, ни подготовленных выражений нет.

```powershell
$env:DIRECT_DATABASE_URL = 'postgres://postgres.<ref>:<пароль>@<хост>:5432/postgres'
pnpm db:migrate --allow-remote=<хост>
Remove-Item Env:DIRECT_DATABASE_URL
```

`<хост>` — ровно имя хоста из строки подключения, без порта, пользователя и базы:

- прямое подключение — `db.<ref>.supabase.co`, требует IPv6 у вашего провайдера;
- сессионный пулер — `aws-0-<регион>.pooler.supabase.com`, работает всегда.

Имя в флаге сверяется с фактическим хостом посимвольно: подставите другое — страж
откажет. Флаг из истории оболочки не разрешает следующую, уже другую цель — это
и есть смысл правила.

Ожидаемый вывод перед запуском (пароля в нём нет намеренно):

```
Цель: <хост>:5432/postgres
Источник: DIRECT_DATABASE_URL — окружение оболочки
Нелокальная цель подтверждена в команде: --allow-remote=<хост>
Выполняю: drizzle-kit migrate
```

Третья строка — `Remove-Item` — обязательна, и вот почему. Переменная в оболочке
сильнее `.env` для **всех** команд `db:*`, а читают они разные переменные:
`db:migrate` идёт через `drizzle-kit` и предпочитает `DIRECT_DATABASE_URL`,
а `db:seed` — это приложение, оно знает только `DATABASE_URL` (`src/db/client.ts`).
Оставленный в оболочке `DIRECT_DATABASE_URL` даст расхождение: страж назовёт
и потребует подтвердить хост Supabase, а сид уйдёт туда, куда указывает
`DATABASE_URL` из `.env` — то есть в локальную базу.

Проверки после миграций, в SQL Editor Supabase:

```sql
select count(*) as applied from drizzle.__drizzle_migrations;         -- ожидается 19
select extname from pg_extension where extname = 'btree_gist';        -- одна строка
select has_table_privilege('anon', 'users', 'SELECT') as anon_reads;  -- false
```

Девятнадцать — сегодняшнее число миграций (`src/db/migrations-manifest.ts`,
`EXPECTED_MIGRATIONS` — длина списка). Оно растёт с каждой новой миграцией;
сверяйте с той сборкой, которую разворачиваете, а не с этой строкой.

Пустой ответ про `btree_gist` — не ошибка деплоя: миграция при нехватке прав
выдаёт `WARNING`, а не падает. Тогда от роли с правом `CREATE` на базе:
`create extension if not exists btree_gist;`. Без расширения не создастся
ограничение `EXCLUDE` на `bed_assignments`, которое не даёт занять одно место
двумя проживаниями.

## 2. Очистка от демо-сида

**Перед началом убедитесь, что вход суперадмином (`+77010000000`) работает.**
После очистки это единственная учётная запись в базе, а пароль существующей
записи сид не меняет: потеряв его, войти будет некем.

Что остаётся: организация, суперадмин, три типа документов, шаблон договора
и пять счетов сети (депозитный фонд, коммунальный фонд, общий счёт, касса, Kaspi).
Типы документов и шаблон договора оставлены не из осторожности: экрана и API
для них нет, заводит их только сид — а он вместе с ними вернёт и пять демо-домов.

Что уходит: пять домов, пять админов, все жильцы с профилями, места и комнаты,
зоны с чек-листами, ряды ротаций и расписание, фонды домов, проводки, счета
на оплату, аудит, сессии, файлы, уведомления, настройки домов.

Скрипт целиком — в `cleanup.sql` в корне репозитория, запускается psql:

```bash
psql "postgres://postgres.<ref>:<пароль>@<хост>:5432/postgres" -f cleanup.sql
```

Текст скрипта здесь намеренно не приводится: копия длинной строки со списком
сохраняемых таблиц однажды потеряла хвост, и очистка стёрла лишнее (инцидент
ниже). Единственный источник — сам файл, запускать его через `-f`, не вставляя
содержимое в чужое окно.

Скрипт устроен так: `\set ON_ERROR_STOP on`, затем одна транзакция, внутри —
проверка списка сохраняемых таблиц, `truncate` всего остального, удаление
демо-домов с их админами и фондами, `commit` и отчёт. Проверка списка
останавливает очистку, если имён в нём не шесть или какого-то из них нет
в схеме `public`.

В SQL Editor Supabase скрипт запускать не нужно и не стоит: `\set` — команда
psql, а вставка руками возвращает ровно ту опасность, из-за которой инцидент
и случился.

Почему `house_id` у админов не обнуляется: проверка `users_admin_has_house`
(миграция 0001) требует дома у роли `admin` и запрещает его у всех остальных —
`update users set house_id = null` падает на первом же админе. Шаг был к тому же
лишним: админы уходят целыми строками следующим `delete`, и дома после этого
никем не заняты. Ошибку нашли вы на репетиции 8 сентября 2026, в скрипте её нет.

Почему не `delete from houses` сразу: все внешние ключи в схеме объявлены
`on delete no action`, каскада нет ни одного — удаление дома с жильцами просто
откажет. Почему `truncate` без `cascade`: в списке уже все таблицы, которые
ссылаются на что-либо внутри него, а из шести оставшихся ссылки идут только
на `organizations` и `houses`, которых `truncate` не касается. `cascade` здесь
был бы опасен ровно наоборот — он утянул бы `users` вместе с суперадмином.

Схема, индексы и миграции не затрагиваются: таблица учёта миграций лежит
в схеме `drizzle`, а не в `public`.

Последним запросом скрипт печатает отчёт — его и надо сверить:

```sql
select
  (select count(*) from houses)             as houses,          -- 0
  (select count(*) from users)              as users,           -- 1
  (select count(*) from organizations)      as organizations,   -- 1
  (select count(*) from accounts)           as accounts,        -- 5
  (select count(*) from document_types)     as document_types,  -- 3
  (select count(*) from contract_templates) as templates,       -- 1
  (select count(*) from residencies)        as residencies;     -- 0
```

Отчёт идёт после `commit` намеренно: он показывает то, что уже записано,
а не то, что видно внутри незавершённой транзакции. Повторный запуск скрипта
безопасен — очищать нечего, все три `delete` трогают ноль строк.

Три предупреждения:

- **`pnpm db:seed` на боевой базе после очистки не запускать.** Он идемпотентен,
  но не «умный»: увидев пустую сеть, он заново заведёт пять домов «Дом 1» — «Дом 5»,
  пятерых админов и несколько десятков демо-жильцов. Сид — инструмент разработки
  и превью, а не боевой установки.
- Файлы демо-жильцов останутся в хранилище: строки в `files` уйдут, байты — нет.
  При `STORAGE_DRIVER=local` это каталог `storage/`, при `gdrive` — папка приложения
  на Диске. Удаляются руками.
- Аудит очищается вместе с остальным, и сама ручная чистка в `audit_log` не пишется:
  журнал боевой базы начнётся с чистого листа. Это осознанно — иначе в нём навсегда
  осталась бы история демо-действий.

Дальше — через интерфейс суперадмина, в этом порядке:

1. `/settings/houses` — реальные дома. Слаг входит в путь хранения документов,
   поэтому задаётся осмысленно и потом не меняется.
2. `/settings/users` — админ на каждый дом.
3. `/settings/house` в контексте дома — комнаты, места с ценами, зоны и чек-листы.
4. `/settings/network` — настройки сети; шаблон договора и типы документов
   уже на месте с прошлого сида.
5. Только после этого — заселение реальных жильцов.

# Инцидент 8 сентября: очистка стёрла скелет сети

## Что случилось

На боевой базе после очистки обнулились `accounts`, `document_types`
и `contract_templates` — вместо 5/3/1 нули. Организация и суперадмин уцелели,
дома и жильцы ушли как задумано.

## Почему — пока неизвестно. Прежний ответ снят

Я утверждал, что список сохраняемых таблиц потерял хвост при переносе. Вы
запускали полный список одной строкой, и `DELETE 0` в выводе не было — версия
не годится. Причина не найдена, вопрос открыт, и ниже написано ровно то,
что проверено, а не то, что похоже на правду.

Проверено после вашего ответа, на локальном PostgreSQL 16 со схемой из тех же
девятнадцати миграций и полным сидом:

- скрипт с полным списком счета, типы документов и шаблон не трогает: после
  прогона 5/3/1 на месте. `NOTICE` печатает список из 47 таблиц — ни одного
  из шести сохраняемых имён в нём нет;
- `truncate` не может увести строки из таблицы, которой нет в списке: он
  затрагивает только перечисленные и их потомков по наследованию, а наследования
  в схеме нет. `cascade` в скрипте не используется;
- каскадных удалений в схеме нет вовсе: все внешние ключи объявлены
  `on delete no action` — поэтому `delete from houses` не мог утянуть счета,
  а `delete from users` — типы документов;
- шаг `delete from accounts where house_id is not null` оставляет счета сети:
  у них `house_id` пуст.

Отсюда следует, что либо на боевой базе выполнялся не тот текст, что лежит
в `cleanup.sql`, либо этих строк там не было ещё до очистки. Различить эти два
случая отсюда нельзя — нужна ваша база.

## Три запроса, которые закрывают вопрос (все только читают)

Первый: были ли строки вообще. Счётчик вставок накопительный, `truncate`
его не сбрасывает:

```sql
select relname, n_tup_ins, n_tup_del, n_live_tup
  from pg_stat_user_tables
 where relname in ('accounts', 'document_types', 'contract_templates')
 order by relname;
```

- `n_tup_ins = 0` — строк не было никогда. Тогда очистка ни при чём: сид
  на боевой базе выполнялся сборкой, в которой этих таблиц ещё не было
  (счета, типы документов и шаблон появились в фазах 2 и 3), а дома
  с их фондами вы заводили через интерфейс — этим объясняется и отсутствие
  `DELETE 0`, потому что фонды домов удалялись настоящими строками.
- `n_tup_ins` больше нуля при `n_live_tup = 0` — строки были и стёрты.
  `n_tup_del = 0` рядом означает, что стёр их `truncate`, а не `delete`.

Второй, если строки всё-таки были: точный текст выполненного `truncate`.
На Supabase `pg_stat_statements` включён по умолчанию и пишет в том числе
служебные команды:

```sql
select calls, query
  from pg_stat_statements
 where query ilike '%truncate%'
 order by calls desc
 limit 20;
```

В строке будет виден список таблиц ровно таким, каким его получил сервер.
Если в нём есть `public.accounts`, `public.document_types`
или `public.contract_templates` — до сервера дошёл не тот текст, что в файле,
и дальше вопрос только в том, где он изменился. Если их там нет, а строки
пропали — причина не в очистке, и искать надо в другом месте.

То же самое, но человеческим экраном: **Advisors → Query Performance**
в дашборде Supabase, и **History** в SQL Editor, где хранятся запущенные
из него запросы.

## Что сделано, пока причина не найдена

Скрипт теперь защищён от результата, а не от версии причины: перед `truncate`
он запоминает количество строк в шести сохраняемых таблицах, а после `truncate`
сверяет. Если хоть одна похудела — исключение, транзакция откатывается целиком,
база остаётся нетронутой. Что именно увело строки — урезанный список, каскад,
триггер или что-то ещё, чего я не предвидел, — для этой проверки неважно.

Проверено на живой базе негативной фикстурой: в список очистки силой добавлен
`document_types`, прогон оборвался сообщением «Очистка задела скелет сети
(document_types: было 3, стало 0). Транзакция откачена», код возврата 3,
база осталась полной — 5 домов, 46 записей, 40 проживаний.

Перед `commit` добавлена вторая проверка: если после очистки в сети нет ни типов
документов, ни шаблона, ни счетов сети, ни учётных записей — тоже отказ
и откат, с подсказкой сначала восстановить скелет. Прежние проверки списка
(длина и существование таблиц) оставлены как были.


## Восстановление

Три сущности возвращает сид в режиме скелета — без домов, админов и жильцов:

```powershell
$env:DATABASE_URL = 'postgres://postgres.<ref>:<пароль>@aws-0-ap-south-1.pooler.supabase.com:6543/postgres?pgbouncer=true'
pnpm db:seed --skeleton --allow-remote=aws-0-ap-south-1.pooler.supabase.com
Remove-Item Env:DATABASE_URL
```

Одного `DATABASE_URL` достаточно: остальные переменные страж `db:*` берёт
из вашего локального `.env` и передаёт команде сам. До 8 сентября он этого
не делал — ни `tsx`, ни `drizzle-kit` файл не читают, — и сид падал на разборе
окружения, требуя `DEPLOY_TARGET`, `APP_URL`, `SESSION_SECRET`,
`FIELD_ENCRYPTION_KEY`, `CRON_SECRET` и `STORAGE_DRIVER`. Порядок остался
прежним: заданное в оболочке сильнее файла.

Убедитесь, что `DIRECT_DATABASE_URL` в оболочке не задан: сид читает только
`DATABASE_URL`, а страж выбирает цель начиная с `DIRECT_DATABASE_URL` —
разойдясь, они назовут одну базу, а изменят другую.

Значения из `.env` — локальные (`STORAGE_DRIVER`, `APP_URL`, ключи). Сид ими
не пользуется: он пишет только в базу, на которую указывает `DATABASE_URL`.
`FIELD_ENCRYPTION_KEY` в скелете не участвует — шифруются им поля жильцов,
которых скелет не создаёт.

Ожидаемый вывод:

```
Сеть готова, домов сид не заводил.

Учётные записи (пароль меняется при первом входе):
  +77010000000  superadmin  вся сеть  уже существует, пароль не менялся

Скелет сети на месте:
  типов документов: 3
  шаблонов договора: 1
  счетов сети: 5
Домов, жильцов и расписания скелет не заводит.
```

Пароль существующего суперадмина сид не трогает, домов не заводит, повторный
запуск безопасен: всё, что уже есть, он пропускает.

Проверено на локальном PostgreSQL дважды: на чистой базе (19 миграций и сразу
`--skeleton`) и на базе в том состоянии, в каком сейчас боевая — полный сид,
очистка, затем удаление счетов, типов и шаблона. После `--skeleton` вернулись
пять счетов сети с кодами `cash`, `common_fund`, `deposit_fund`, `kaspi`,
`utility_fund`, три типа документов и активный шаблон договора; домов ноль,
суперадмин со своим прежним паролем.

Фонды домов (`house_fund:<слаг>`) восстанавливать не нужно: `createHouse`
заводит фонд каждому новому дому сам.

## Почему эти три сущности заводит только сид

Дыра есть, но не в фазе 6, а в модулях 10 и 11, и она старше:

- **Типы документов и сроки годности** — модуль 11, «Настройки сети (суперадмин)».
  Экрана нет. T2.8 завёл таблицу и сид, редактор не делал.
- **Шаблон договора** — модуль 11 требует HTML-редактор с палитрой токенов,
  предпросмотром на тестовых данных и версионированием. Экрана нет. T2.9 завёл
  базовый шаблон сидом, редактор не делал.
- **План счетов** — модуль 10: «Список счетов: код, название, тип, дом, остаток.
  Создание, переименование, архивация». Экрана нет. Репозиторий
  `src/db/repositories/accounts.ts` умеет создавать счета, но ни один сервис
  и ни один экран его не зовут — счета появляются только из сида.

Ни в одном списке тасков этих экранов нет: они выпали при разбиении фаз, а не
были отложены осознанно. Заметить это было нечем — сид всегда приносил и типы,
и шаблон, и счета, а очистка боевой базы впервые оставила сеть без них.
Экран `/settings/network` сейчас закрывает из модуля 11 ровно две строки:
видимость рейтинга у жильцов и локаль по умолчанию.

Это работа на отдельную фазу: три экрана, права суперадмина, записи в `audit_log`,
три локали, приёмки. Версионирование шаблона договора тянет за собой миграцию:
колонка `version` в `contract_templates` есть, но менять шаблон, не ломая уже
собранные договоры, значит хранить историю версий и ссылаться на неё
из `residencies`. Скажите слово — распишу на таски и начну.

# Оценка: дополнительные поля профиля (не начато, ждёт вашего слова)

Задумка: суперадмин объявляет поле в настройках — название, тип, обязательность, —
оно появляется в форме заселения и становится токеном шаблона договора.

**Объём: пять тасков.** Дело не в самой форме, а в том, что три вещи, которые
сейчас известны на этапе сборки, становятся данными: набор полей профиля,
палитра токенов и правила проверки.

1. Хранилище: `profile_field_defs` (`org_id`, `code`, `name_i18n`, тип,
   обязательность, порядок, `archived_at`) и `profile_field_values`
   (`user_id`, `field_id`, значение). Отдельная таблица значений, а не JSONB
   в `resident_profiles`: изменение значения обязано попадать в `audit_log`
   построчно, а по объявленному полю нужен поиск. Типы — строка, число, дата,
   да/нет, выбор из списка: пять, а не «любой», иначе проверка станет гаданием.
2. Форма заселения и профиль: поля рисуются по объявлению, схема zod собирается
   в рантайме, обязательность проверяется на сервере, а не только в браузере.
   Три локали берутся из `name_i18n`, а не из словарей.
3. Экран объявления полей у суперадмина: список, создание, переименование,
   архивация. Архивация вместо удаления: значения остаются в уже собранных
   договорах и в истории.
4. Токены шаблона: палитра дополняется `profile.<код>`. Здесь ломается больше
   всего — см. ниже.
5. Приёмка e2e: суперадмин объявляет поле, оно требуется при заселении,
   попадает в договор и остаётся в старом договоре после архивации.

**Что ломает.** Четыре места, каждое проверяемое:

- `unknownTokens()` в `src/domain/contract-template.ts` — чистая функция над
  константным списком: ей достаточно текста шаблона. С объявляемыми полями
  палитра приходит из базы, и проверка шаблона перестаёт быть чистой. Чинится
  тем, что список токенов передаётся аргументом, а не импортируется, — но это
  правка во всех вызовах и в тестах.
- Предпросмотр шаблона на тестовых данных должен откуда-то брать значения
  для объявленных полей: понадобится образец на каждый тип.
- Спецификация OpenAPI для профиля перестаёт быть статической: либо поля
  уходят в свободный объект (и бот теряет описание), либо спецификация
  собирается по объявлениям на каждый запрос.
- Архивированное поле обязано остаться читаемым в старом договоре, иначе
  документ, который уже подписан, начнёт собираться иначе. Это то же
  требование, что и версионирование шаблона в T8.5, и делать их порознь
  дороже: разумно ставить эту работу сразу после фазы 8, чтобы обе истории
  опирались на одну версионность.

**Сроков не называю**, пока не закрыт T8.5: версионирование шаблона покажет,
сколько на самом деле стоит «старый документ не меняется задним числом».
