# Деплой на Vercel + Supabase

Инструкция для владельца. Две части: разделы 1-7 — превью-деплой, разделы 8-11 —
боевая база Supabase.

Цель превью — поднять каркас фазы 0 на настоящем serverless-рантайме и убедиться
в том, что локальная сборка проверить не может: пулер соединений, лимит тела
запроса, поведение edge/serverless.

Локальная команда `DEPLOY_TARGET=vercel pnpm build` подтверждает **только** сборку бандла.

# Превью-деплой

## 1. Supabase: база данных

1. Создайте проект на [supabase.com](https://supabase.com). Регион — ближайший к Алматы
   (`Southeast Asia` или `Central EU`; на скорость холодного старта влияет несильно,
   на задержку запросов — заметно).
2. Задайте пароль базы и сохраните его.
3. В **Project Settings → Database → Connection string** возьмите **две** строки:

| Переменная | Где взять | Порт | Для чего |
|---|---|---|---|
| `DATABASE_URL` | Connection pooling, режим **Transaction** | 6543 | рантайм приложения |
| `DIRECT_DATABASE_URL` | Direct connection | 5432 | миграции drizzle-kit |

К строке пулера добавьте `?pgbouncer=true`:

```
postgres://postgres.<ref>:<пароль>@aws-0-<регион>.pooler.supabase.com:6543/postgres?pgbouncer=true
```

Почему две строки: в режиме transaction pooling нельзя выполнять DDL и подготовленные
выражения. Приложение ходит через пулер (`prepare: false`, пул в одно соединение —
это уже сделано в `src/db/client.ts`), а миграции идут напрямую.

## 1а. Выключить Data API проекта (обязательный шаг)

Интеграция Supabase кладёт в проект переменные `NEXT_PUBLIC_SUPABASE_URL`
и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. **Приложение их не читает** — можно удалить.
Оставленные, они безвредны сами по себе, но указывают на настоящую проблему.

Мы намеренно не используем RLS: авторизация живёт в приложении, одна точка правды
(решение D6). На Supabase это опасное сочетание. Проект по умолчанию отдаёт наружу
Data API (PostgREST), а роли `anon` и `authenticated` по умолчанию получают права
на схему `public` — ту самую, где лежат наши таблицы. Публикуемый ключ на то и
публикуемый, что он попадает в браузер. В связке с выключенным RLS это означает
чтение и запись данных напрямую, мимо `authz.ts` целиком.

Миграция `0004_lock_down_supabase_data_api` отзывает у этих ролей права на схему
и на будущие объекты, поэтому после прогона миграций дыра закрыта. На обычном
PostgreSQL ролей `anon` и `authenticated` нет, и там миграция ничего не делает.

**Выключите Data API сразу после создания проекта, до первого деплоя:**
**Project Settings → API → Data API**, убрать `public` из списка отдаваемых схем.
Мы к нему не обращаемся ни одной строкой кода, поэтому терять нечего.

Проверить изнутри базы:

```sql
select has_table_privilege('anon', 'users', 'SELECT') as anon_reads_users;
```

Ожидается `false`.

Проверить снаружи, публикуемым ключом:

```bash
curl -s "https://<ref>.supabase.co/rest/v1/users?select=*"   -H "apikey: <публикуемый ключ>"
```

Ожидается `PGRST002` — PostgREST не может построить кэш схемы, данные не отдаются.
Это состояние проверено на живом проекте 6 сентября 2026.

**При создании любой новой схемы** защиту нужно повторить: миграция 0004 покрывает
только `public`. Чек-лист — в `CLAUDE.md` §3.

## 2. Миграции

Миграции **не** выполняются при сборке на Vercel: сборка не должна менять базу.
Прогоните их со своей машины перед первым деплоем:

```bash
DIRECT_DATABASE_URL='postgres://postgres.<ref>:<пароль>@<хост>:5432/postgres' \
  pnpm db:migrate --allow-remote=<хост>
```

Перед запуском команда печатает цель и то, откуда взята строка подключения.
Без `--allow-remote=<хост>` она остановится: нелокальная база требует явного
подтверждения в самой команде (`CLAUDE.md` §5). Имя хоста в флаге должно совпадать
с фактическим — иначе подтверждение не принимается.

Затем проверьте, что расширение `btree_gist` действительно установилось:

```sql
select extname from pg_extension where extname = 'btree_gist';
```

Миграция написана так, что при нехватке прав она не падает, а выдаёт `WARNING`.
Поэтому пустой результат этого запроса — не ошибка деплоя, а сигнал, что расширение
нужно поставить вручную от роли с правом `CREATE` на базе:

```sql
create extension if not exists btree_gist;
```

Без него в фазе 2 не создастся ограничение `EXCLUDE` на `bed_assignments`,
которое запрещает занимать одно место двумя проживаниями одновременно.

**Запишите результат этой проверки в `docs/08-DECISIONS.md`** — там висит
соответствующий `[ОТКРЫТО]`.

## 3. Проект на Vercel

1. **Add New → Project**, импортируйте репозиторий.
2. Framework Preset определится как Next.js. Команды установки и сборки заданы
   в `vercel.json`, менять их в интерфейсе не нужно.
3. Node.js Version — **24.x**.

## 4. Переменные окружения

Задаются в **Settings → Environment Variables**. Отметьте окружения
Production и Preview.

| Переменная | Значение | Обязательна в фазе 0 |
|---|---|---|
| `DEPLOY_TARGET` | `vercel` | да |
| `DATABASE_URL` | строка пулера, порт 6543, `?pgbouncer=true` | да |
| `DIRECT_DATABASE_URL` | прямая строка, порт 5432 | нет (нужна только для миграций) |
| `APP_URL` | адрес развёртывания, например `https://nice-almaty.vercel.app` | да |
| `SESSION_SECRET` | случайная строка не короче 32 символов | да |
| `FIELD_ENCRYPTION_KEY` | 32 байта в base64: `openssl rand -base64 32` | да |
| `CRON_SECRET` | случайная строка не короче 16 символов | да |
| `STORAGE_DRIVER` | `local` для первого превью | да |
| `LOCAL_STORAGE_PATH` | `/tmp/storage` | **да, при `STORAGE_DRIVER=local`** |
| `DEFAULT_LOCALE` | `ru` | нет, по умолчанию `ru` |
| `TZ` | `Asia/Almaty` | нет |
| `GDRIVE_*` | три ключа OAuth; `GDRIVE_ROOT_FOLDER_ID` необязателен | только при `STORAGE_DRIVER=gdrive` |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_STORAGE_BUCKET` | — | только при `STORAGE_DRIVER=supabase` |
| `WEBPUSH_*` | три ключа | нет; задаются все три или ни одного |

Пустые значения оставлять можно: они считаются незаданными.

Про `STORAGE_DRIVER` на первом превью: драйверы `gdrive` и `supabase` появятся в фазе 2,
сейчас они отвечают `skipped`.

**`LOCAL_STORAGE_PATH` обязательно поменять на `/tmp/storage`.** Значение по умолчанию
`./storage` на Vercel не работает: файловая система функции доступна только на чтение,
писать можно лишь в `/tmp`. А `/api/health` при драйвере `local` пробует записать и удалить
пробный файл — на `./storage` он получит отказ и вернёт `503`. То есть первая же проверка
из следующего раздела упала бы по причине, не имеющей отношения к работоспособности
приложения.

Каталог `/tmp` живёт до перезапуска функции и не общий между экземплярами: для проверки
живости этого достаточно, для хранения документов — разумеется, нет.

## 5. Что проверить после деплоя

1. `GET /api/health` — должен вернуть `200` и такое тело:

   ```json
   { "status": "ok", "checks": { "database": { "status": "ok" }, "storage": { "status": "ok", "driver": "local" } } }
   ```

   Если база отвечает ошибкой — почти наверняка в `DATABASE_URL` подставлена
   прямая строка вместо пулера или потерян `?pgbouncer=true`.
   С `?pdf=1` в ответе появляется раздел `pdf` — проверка печати договора
   (раздел «Печать договора на Vercel»).

2. Откройте главную. Ожидается боковое меню и заголовок «Дэшборд».
3. Переключите тему на тёмную, перезагрузите страницу — вспышки светлого фона быть не должно.
4. Переключите язык на «Қазақша» и «English», перезагрузите — выбор сохраняется в cookie.
5. Откройте с телефона: внизу должна быть навигация из четырёх пунктов и «Ещё»,
   горизонтальной прокрутки быть не должно.

## 5.1. Миграции перед деплоем

Порядок обязателен: сначала миграции, потом приложение. Обратный порядок даёт
работающий наполовину экземпляр — приложение специально проверяет версию схемы
при первом обращении к базе и падает понятной ошибкой, если она отстала.

```bash
# из локальной машины, по прямому подключению (не через пулер)
DIRECT_DATABASE_URL=postgres://... pnpm db:migrate --allow-remote=<хост Supabase>
```

Прямое подключение, а не пулер: `drizzle-kit` выполняет DDL, а transaction pooling
его не поддерживает. Флаг `--allow-remote` называет хост явно — страж подключения
не пускает команду в нелокальную базу без него (CLAUDE.md §5).

Автодеплой Vercel миграции не применяет и не должен: выкатка кода и изменение
схемы — разные действия с разной ценой ошибки. Если схема отстала, приложение
скажет об этом само.

## 5.2. Сид на превью

После миграций сеть пуста: ни домов, ни учётных записей, войти некому.

```bash
DATABASE_URL='<строка пулера>' pnpm db:seed
```

Сид печатает временные пароли один раз — сохраните их. Повторный запуск ничего
не удваивает и паролей больше не покажет: в базе лежит только их хеш.

## 6. Расписание заданий

В `vercel.json` секции `crons` **нет** намеренно: обработчиков `/api/v1/cron/*`
ещё не существует, включённое расписание давало бы ежедневные 404.

Готовый блок лежит в `vercel.crons.example.json` — времена уже переведены
из `Asia/Almaty` в UTC. Его нужно перенести в `vercel.json` в фазе 6.

Учтите два ограничения платформы:

- на тарифе Hobby число cron-заданий ограничено, а частота — не чаще суточной;
  десять заданий из `01-ARCHITECTURE.md` требуют платного тарифа. Поэтому
  `notifications-dispatch`, который идёт каждые пять минут, в `vercel.json`
  не переносится: платформа отклонила бы весь файл, вместе с суточными
  заданиями, которые там уже работают. На Vercel очередь разбирается внешним
  вызовом `POST /api/v1/cron/notifications-dispatch` (P1-5, P6-9);
- в выражениях Vercel нет `L` (последний день месяца), поэтому месячные задания
  запускаются ежедневно и сами проверяют дату по календарю Алматы.

## 7. Ограничения, о которых нужно помнить

- **Тело запроса ~4.5 МБ.** Поэтому загрузка файлов всегда двухшаговая:
  сессия загрузки, прямая отправка байтов в хранилище, подтверждение.
  Это заложено в архитектуру и не зависит от окружения (фаза 2).
- **Файловая система временная.** Писать в неё в проде нельзя, только через `StorageProvider`.
- **Node-only API нельзя тащить в edge-рантайм.** Логгер `pino` рассчитан на Node.
- **Пулер и DDL.** Любая операция, меняющая схему, идёт через `DIRECT_DATABASE_URL`.

## Печать договора на Vercel

В serverless нет системного chromium, поэтому для `DEPLOY_TARGET=vercel`
печатает сборка `@sparticuz/chromium`. С 9 сентября 2026 пакет лежит
в зависимостях проекта (P9-2): боевая собирается из репозитория, и указание
«добавьте его перед деплоем» оставляло боевую без него — договор отвечал
`contract.errors.unknown` (инцидент I12). Ставить ничего не нужно.
`CHROMIUM_PATH` на Vercel не задаётся: путь приходит из самого пакета.

Версии связаны: `puppeteer-core` ждёт определённый Chrome, и мажорная
версия `@sparticuz/chromium` обязана с ним совпадать (сейчас 152 и 152).
Обновляя одно, обновляйте другое.

Проверка после деплоя — `GET /api/health?pdf=1`: раздел `pdf` должен ответить
`{"status":"ok","driver":"chromium"}`. Запрос поднимает браузер и идёт
несколько секунд; без `?pdf=1` печать не проверяется. Ответ `error` содержит
причину целиком.

## 8. Миграции против боевой Supabase

Строка для миграций — прямое подключение или **сессионный** пулер, порт 5432.
Транзакционный пулер (6543) не годится: `drizzle-kit` выполняет DDL, а в режиме
transaction pooling ни DDL, ни подготовленных выражений нет.

```powershell
$env:DIRECT_DATABASE_URL = 'postgres://postgres.<ref>:<пароль>@<хост>:5432/postgres'
pnpm db:migrate --allow-remote=<хост>
Remove-Item Env:DIRECT_DATABASE_URL
```

`<хост>` — ровно имя хоста из строки подключения, без порта, пользователя и базы:

- прямое подключение — `db.<ref>.supabase.co`, требует IPv6 у вашего провайдера;
- сессионный пулер — `aws-0-<регион>.pooler.supabase.com`, работает всегда.

Имя в флаге сверяется с фактическим хостом посимвольно: подставите другое — страж
откажет. Флаг из истории оболочки не разрешает следующую, уже другую цель — это
и есть смысл правила.

Ожидаемый вывод перед запуском (пароля в нём нет намеренно):

```
Цель: <хост>:5432/postgres
Источник: DIRECT_DATABASE_URL — окружение оболочки
Нелокальная цель подтверждена в команде: --allow-remote=<хост>
Выполняю: drizzle-kit migrate
```

Третья строка — `Remove-Item` — обязательна, и вот почему. Переменная в оболочке
сильнее `.env` для **всех** команд `db:*`, а читают они разные переменные:
`db:migrate` идёт через `drizzle-kit` и предпочитает `DIRECT_DATABASE_URL`,
а `db:seed` — это приложение, оно знает только `DATABASE_URL` (`src/db/client.ts`).
Оставленный в оболочке `DIRECT_DATABASE_URL` даст расхождение: страж назовёт
и потребует подтвердить хост Supabase, а сид уйдёт туда, куда указывает
`DATABASE_URL` из `.env` — то есть в локальную базу.

Проверки после миграций, в SQL Editor Supabase:

```sql
select count(*) as applied from drizzle.__drizzle_migrations;         -- ожидается 21
select extname from pg_extension where extname = 'btree_gist';        -- одна строка
select has_table_privilege('anon', 'users', 'SELECT') as anon_reads;  -- false
```

Двадцать один — сегодняшнее число миграций (`src/db/migrations-manifest.ts`,
`EXPECTED_MIGRATIONS` — длина списка). Оно растёт с каждой новой миграцией;
сверяйте с той сборкой, которую разворачиваете, а не с этой строкой.

Пустой ответ про `btree_gist` — не ошибка деплоя: миграция при нехватке прав
выдаёт `WARNING`, а не падает. Тогда от роли с правом `CREATE` на базе:
`create extension if not exists btree_gist;`. Без расширения не создастся
ограничение `EXCLUDE` на `bed_assignments`, которое не даёт занять одно место
двумя проживаниями.

## 9. Очистка от демо-сида

**Перед началом убедитесь, что вход суперадмином (`+77010000000`) работает.**
После очистки это единственная учётная запись в базе, а пароль существующей
записи сид не меняет: потеряв его, войти будет некем.

Что остаётся: организация, суперадмин, три типа документов, шаблон договора
и пять счетов сети (депозитный фонд, коммунальный фонд, общий счёт, касса, Kaspi).
Типы документов и шаблон договора оставлены не из осторожности: экрана и API
для них нет, заводит их только сид — а он вместе с ними вернёт и пять демо-домов.

Что уходит: пять домов, пять админов, все жильцы с профилями, места и комнаты,
зоны с чек-листами, ряды ротаций и расписание, фонды домов, проводки, счета
на оплату, аудит, сессии, файлы, уведомления, настройки домов.

Скрипт целиком — в `cleanup.sql` в корне репозитория, запускается psql:

```bash
psql "postgres://postgres.<ref>:<пароль>@<хост>:5432/postgres" -f cleanup.sql
```

Текст скрипта здесь намеренно не приводится: копия длинной строки со списком
сохраняемых таблиц однажды потеряла хвост, и очистка стёрла лишнее (инцидент I9
в `docs/08-DECISIONS.md`). Единственный источник — сам файл, запускать его через `-f`, не вставляя
содержимое в чужое окно.

Скрипт устроен так: `\set ON_ERROR_STOP on`, затем одна транзакция, внутри —
проверка списка сохраняемых таблиц, `truncate` всего остального, удаление
демо-домов с их админами и фондами, `commit` и отчёт. Проверка списка
останавливает очистку, если имён в нём не шесть или какого-то из них нет
в схеме `public`.

В SQL Editor Supabase скрипт запускать не нужно и не стоит: `\set` — команда
psql, а вставка руками возвращает ровно ту опасность, из-за которой инцидент
и случился.

Почему `house_id` у админов не обнуляется: проверка `users_admin_has_house`
(миграция 0001) требует дома у роли `admin` и запрещает его у всех остальных —
`update users set house_id = null` падает на первом же админе. Шаг был к тому же
лишним: админы уходят целыми строками следующим `delete`, и дома после этого
никем не заняты. Ошибку нашли вы на репетиции 8 сентября 2026, в скрипте её нет.

Почему не `delete from houses` сразу: все внешние ключи в схеме объявлены
`on delete no action`, каскада нет ни одного — удаление дома с жильцами просто
откажет. Почему `truncate` без `cascade`: в списке уже все таблицы, которые
ссылаются на что-либо внутри него, а из шести оставшихся ссылки идут только
на `organizations` и `houses`, которых `truncate` не касается. `cascade` здесь
был бы опасен ровно наоборот — он утянул бы `users` вместе с суперадмином.

Схема, индексы и миграции не затрагиваются: таблица учёта миграций лежит
в схеме `drizzle`, а не в `public`.

Последним запросом скрипт печатает отчёт — его и надо сверить:

```sql
select
  (select count(*) from houses)             as houses,          -- 0
  (select count(*) from users)              as users,           -- 1
  (select count(*) from organizations)      as organizations,   -- 1
  (select count(*) from accounts)           as accounts,        -- 5
  (select count(*) from document_types)     as document_types,  -- 3
  (select count(*) from contract_templates) as templates,       -- 1
  (select count(*) from residencies)        as residencies;     -- 0
```

Отчёт идёт после `commit` намеренно: он показывает то, что уже записано,
а не то, что видно внутри незавершённой транзакции. Повторный запуск скрипта
безопасен — очищать нечего, все три `delete` трогают ноль строк.

Три предупреждения:

- **`pnpm db:seed` на боевой базе после очистки не запускать.** Он идемпотентен,
  но не «умный»: увидев пустую сеть, он заново заведёт пять домов «Дом 1» — «Дом 5»,
  пятерых админов и несколько десятков демо-жильцов. Сид — инструмент разработки
  и превью, а не боевой установки.
- Файлы демо-жильцов останутся в хранилище: строки в `files` уйдут, байты — нет.
  При `STORAGE_DRIVER=local` это каталог `storage/`, при `gdrive` — папка приложения
  на Диске. Удаляются руками.
- Аудит очищается вместе с остальным, и сама ручная чистка в `audit_log` не пишется:
  журнал боевой базы начнётся с чистого листа. Это осознанно — иначе в нём навсегда
  осталась бы история демо-действий.

Дальше — через интерфейс суперадмина, в этом порядке:

1. `/settings/houses` — реальные дома. Слаг входит в путь хранения документов,
   поэтому задаётся осмысленно и потом не меняется.
2. `/settings/users` — админ на каждый дом.
3. `/settings/house` в контексте дома — комнаты, места с ценами, зоны и чек-листы.
4. `/settings/network` — настройки сети; шаблон договора и типы документов
   уже на месте с прошлого сида.
5. Только после этого — заселение реальных жильцов.

## 10. Порядок развёртывания (T7.6)

0. **Боевой `FIELD_ENCRYPTION_KEY` — до первого реального жильца.** ИИН и номера
   удостоверений лежат зашифрованными на этом ключе (AES-256-GCM); смена ключа
   после ввода данных делает их нечитаемыми, обратного пути нет.
1. Проект Supabase создан, **Data API выключен**: Project Settings → API → Data API,
   `public` убран из списка отдаваемых схем. Делается до первого деплоя;
   миграция `0004` закрывает ту же дыру со стороны прав, но выключенный Data API
   надёжнее — он не зависит от того, какой ролью выполнены миграции.
2. **Миграции** — раздел 8 этого файла, с вашей машины, прямым подключением.
   Проверить число миграций, `btree_gist` и права `anon` там же.
3. **Очистка демо-сида** — раздел 9, если база уже видела сид.
4. **Переменные окружения** в целевом окружении. Полная таблица —
   §4 этого файла. Ключевое: `DATABASE_URL` — строка пулера, порт 6543,
   с `?pgbouncer=true`; `DIRECT_DATABASE_URL` в проде не нужен вовсе, он только
   для миграций; `LOCAL_STORAGE_PATH=/tmp/storage` при `STORAGE_DRIVER=local`
   на Vercel, иначе `/api/health` вернёт 503 на попытке записи.
5. **Деплой кода** — строго после миграций. Обратный порядок даёт наполовину
   рабочий экземпляр: приложение проверяет версию схемы и отказывает понятной
   ошибкой с числом применённых и ожидаемых миграций.
6. **Проверки после деплоя.** Здесь важна точность: проверка схемы срабатывает
   в `requireApiActor` (`src/lib/api/route.ts`), то есть на маршрутах `/api/v1/*`.
   `/api/health` её не делает — он проверяет соединение (`select 1`) и хранилище
   и остаётся зелёным на отставшей схеме. Порядок проверок:
   - `GET /api/health` — 200, `database.status = ok`, `storage.status = ok`;
   - счёт миграций в базе против `EXPECTED_MIGRATIONS` сборки;
   - вход суперадмином, открывается дэшборд;
   - любой `/api/v1/*` с боевым токеном — именно он поднимает проверку схемы.
7. **Расписание.** В `vercel.json` три суточных задания уже перенесены.
   `notifications-dispatch` идёт каждые пять минут и на тарифе Hobby невозможен:
   его дёргает внешний вызов `POST /api/v1/cron/notifications-dispatch`
   с заголовком `x-cron-secret`. На VPS всю десятку заданий ведёт `pnpm worker`.
8. **Печать договора на Vercel** ничего не требует: `@sparticuz/chromium`
   в зависимостях с 9 сентября 2026 (P9-2). Проверка — `GET /api/health?pdf=1`.

Про `docker compose` с боевой базой: не выйдет без правки файла. `docker-compose.yml`
жёстко подставляет `DATABASE_URL` на свой контейнер `postgres` всем трём сервисам,
а команда сервиса `migrate` содержит `--allow-remote=postgres` — с хостом Supabase
страж её остановит, и это правильно. Цель развёртывания на Supabase — Vercel,
по разделам 3 и 4 этого файла.

## 11. Восстановление скелета сети

Если боевая сеть осталась без счетов сети, типов документов или шаблона договора
(инцидент I9 в `docs/08-DECISIONS.md`), эти три сущности возвращает сид в режиме
скелета — без домов, админов и жильцов:

```powershell
$env:DATABASE_URL = 'postgres://postgres.<ref>:<пароль>@aws-0-ap-south-1.pooler.supabase.com:6543/postgres?pgbouncer=true'
pnpm db:seed --skeleton --allow-remote=aws-0-ap-south-1.pooler.supabase.com
Remove-Item Env:DATABASE_URL
```

Одного `DATABASE_URL` достаточно: остальные переменные страж `db:*` берёт
из вашего локального `.env` и передаёт команде сам. До 8 сентября он этого
не делал — ни `tsx`, ни `drizzle-kit` файл не читают, — и сид падал на разборе
окружения, требуя `DEPLOY_TARGET`, `APP_URL`, `SESSION_SECRET`,
`FIELD_ENCRYPTION_KEY`, `CRON_SECRET` и `STORAGE_DRIVER`. Порядок остался
прежним: заданное в оболочке сильнее файла.

Убедитесь, что `DIRECT_DATABASE_URL` в оболочке не задан: сид читает только
`DATABASE_URL`, а страж выбирает цель начиная с `DIRECT_DATABASE_URL` —
разойдясь, они назовут одну базу, а изменят другую.

Значения из `.env` — локальные (`STORAGE_DRIVER`, `APP_URL`, ключи). Сид ими
не пользуется: он пишет только в базу, на которую указывает `DATABASE_URL`.
`FIELD_ENCRYPTION_KEY` в скелете не участвует — шифруются им поля жильцов,
которых скелет не создаёт.

Ожидаемый вывод:

```
Сеть готова, домов сид не заводил.

Учётные записи (пароль меняется при первом входе):
  +77010000000  superadmin  вся сеть  уже существует, пароль не менялся

Скелет сети на месте:
  типов документов: 3
  шаблонов договора: 1
  счетов сети: 5
Домов, жильцов и расписания скелет не заводит.
```

Пароль существующего суперадмина сид не трогает, домов не заводит, повторный
запуск безопасен: всё, что уже есть, он пропускает.

Проверено на локальном PostgreSQL дважды: на чистой базе (19 миграций и сразу
`--skeleton`) и на базе в том состоянии, в каком сейчас боевая — полный сид,
очистка, затем удаление счетов, типов и шаблона. После `--skeleton` вернулись
пять счетов сети с кодами `cash`, `common_fund`, `deposit_fund`, `kaspi`,
`utility_fund`, три типа документов и активный шаблон договора; домов ноль,
суперадмин со своим прежним паролем.

Фонды домов (`house_fund:<слаг>`) восстанавливать не нужно: `createHouse`
заводит фонд каждому новому дому сам.
