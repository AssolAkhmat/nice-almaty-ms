# Фаза 8. Настройки сети: типы документов, план счетов, шаблон договора

Источник: `docs/04-MODULES/11-users-settings.md` («Настройки сети»),
`docs/04-MODULES/10-accounting-inventory.md` («Учёт»),
`docs/08-DECISIONS.md` (инцидент I9; указание владельца от 8 сентября 2026 выполнено
и убрано из `docs/OWNER-NOTES.md`).

Фаза закрывает дыру, вскрывшуюся на очистке боевой базы: три сущности из ТЗ
заводит только сид, а экранов у них нет. Порядок задан владельцем: типы
документов, план счетов, шаблон договора последним — он тянет версионирование.

Правило прежнее: один таск = один коммит = зелёный `pnpm verify`.

## Критерии приёмки фазы

- [x] Суперадмин заводит тип документа, меняет срок годности и архивирует его
      без обращения к базе
- [x] Суперадмин видит план счетов с остатками, заводит и переименовывает счёт,
      архивирует несистемный
- [x] Суперадмин правит шаблон договора, вставляет токен кликом, видит
      предпросмотр на тестовых данных и сохраняет новую версию
- [x] Договор, собранный по старой версии шаблона, остаётся читаемым:
      подпись пересобирает документ по своей версии (проверено интеграционно)
- [x] Три поля под договор заполняются в профиле и попадают в токены шаблона
- [x] `pnpm db:seed --skeleton` на чистой базе и экраны фазы дают один и тот же
      результат: сеть, готовую к работе без единого запроса к базе руками

## Чего в этой фазе нет

Дополнительных полей профиля, объявляемых суперадмином (оценка — в
`docs/OWNER-NOTES.md`, решения владельца пока нет). Загрузки готового договора
в docx/pdf как вложения-образца: модуль 11 допускает её как справочную,
подставляемый документ всё равно собирается из HTML-шаблона.

      `src/domain/contract-number.ts` с юнит-тестами, выдача — при заведении
      проживания, а старым проживаниям номер достаётся при первой сборке договора

      `resident.registration_address`, `residency.contract_number`
