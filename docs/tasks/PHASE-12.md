# Фаза 12 — дополнительные поля профиля

Собрана из указания владельца от 21 сентября 2026: «делаем по твоей оценке,
с уточнением: поля бывают обязательные и необязательные, каждое поле становится
токеном шаблона договора. Архивированное поле остаётся читаемым в уже подписанных
договорах». Оценка — `docs/OWNER-NOTES.md`, раздел «дополнительные поля профиля»:
пять тасков. Зависимость снята: версионирование шаблона (T8.5) закрыто.

Суть работы не в форме, а в том, что три вещи, известные сейчас на этапе сборки,
становятся данными: набор полей профиля, палитра токенов договора и правила
проверки. Порядок закрытия обычный: один таск — один коммит — зелёные тесты.

## T12.1 Хранилище объявленных полей

- [x] Миграция: `profile_field_defs` (`org_id`, `code`, `name_i18n`, тип,
      обязательность, порядок, `archived_at`) и `profile_field_values`
      (`user_id`, `field_id`, значение)
- [x] Отдельная таблица значений, а не JSONB в `resident_profiles`: правка
      значения пишется в `audit_log` построчно, по объявленному полю нужен поиск
- [x] Пять типов, а не «любой»: строка, число, дата, да/нет, выбор из списка.
      Негативная фикстура: шестой тип база не принимает
- [x] `code` уникален в сети и не переиспользуется после архивации: токен
      договора обязан значить одно и то же во всех версиях
- [x] Репозиторий `src/db/repositories/profile-fields.ts`, фильтр по `org_id`
- [x] Значение архивированного поля остаётся читаемым, запись нового отвергает
      база (триггер `profile_field_values_match_def`), а не только сервис

## T12.2 Поля в форме заселения и в профиле

- [x] Поля рисуются по объявлению; порядок из `sort_order`, названия
      из `name_i18n` на языке читающего, а не из словарей
- [x] Разбор значений — чистым ядром `src/domain/profile-fields.ts`, а не
      собранной в рантайме схемой zod: правила проверки описаны один раз
      и покрыты числовыми примерами (строка `[ОТКРЫТО]` в D31-разделе решений)
- [x] Обязательность проверяется на сервере, а не только в браузере:
      негативная фикстура — запись мимо формы без обязательного поля
- [x] Шаг «профиль» в мастере заселения не закрывается, пока обязательное
      объявленное поле пусто; фикстура краснеет, если шаг о полях не знает
- [x] Правка значения пишет `audit_log` построчно, с кодом поля; неизменённое
      значение журнал не тревожит
- [x] Архивированное поле в форме не заполняется, но показывается прежним
      значением; без значения не показывается вовсе
- [x] Отказ называет поле и причину подстановками словаря, а не «проверьте
      введённые данные»
- [x] Три локали, ключи журнала для новых сущностей и действий

## T12.3 Экран объявления полей у суперадмина

- [x] Список, объявление, переименование, порядок, архивация и возврат из архива
- [x] Кнопки удаления нет вовсе: на поле ссылаются подписанные договоры
      и карточки жильцов
- [x] Код и тип у заведённого поля не меняются: по коду собран договор,
      сменой типа прежние значения перестали бы разбираться
- [x] Право `settings.org.write` — то же, что у типов документов: набор полей
      правило всей сети. Админу экран не открывается
- [x] Каждая мутация в `audit_log`
- [x] В таблице показан токен договора `profile.<код>`, а не внутренний код
- [x] Предупреждение при архивации поля, чей токен стоит в действующем шаблоне:
      в новых договорах он станет пустым
- [x] Три локали, ссылка из «Настроек»

## T12.4 Токены шаблона `profile.<код>`

- [x] `unknownTokens()` и `renderContractTemplate()` принимают палитру
      аргументом, а не импортируют константу: ядро осталось чистым,
      а набор токенов стал данными. Пустой список — прежнее поведение
- [x] Палитра = постоянные токены плюс объявленные поля сети, включая
      архивированные: их токены стоят в шаблонах, по которым уже собраны
      договоры
- [x] Значение объявленного поля экранируется как любое другое: список
      вставляемых разметкой токенов закрыт подписями. Негативная фикстура —
      разметка в значении поля печатается текстом
- [x] Предпросмотр шаблона: образец на каждый из пяти типов, да/нет и дата
      в человеческом виде на языке сети
- [x] Палитра на экране шаблона показывает и объявленные поля: иначе
      суперадмин не узнал бы, как вставить поле, которое сам завёл
- [x] Договор собирается со значениями на момент сборки; архивация поля
      сборку не ломает — интеграционная фикстура
- [x] Спецификация OpenAPI не меняется: профиля в `/api/v1` нет вовсе
      (есть дома, места, счёта, ротации, инвентарь, файлы). Когда появится,
      объявленные поля войдут в него описанным объектом — строка
      в `docs/tasks/MAINTENANCE.md`
- [x] Решение D31 дополнено

## T12.5 Приёмка

- [x] Суперадмин объявляет поле на экране настроек; код занят навсегда,
      и следующий прогон возвращает поле из архива тем же кодом
- [x] Токен `profile.<код>` виден в палитре экрана шаблона
- [x] Жилец заполняет поле в своём профиле той же формой
- [x] После архивации значение остаётся на экране текстом, а не полем ввода
- [x] Код поля у каждой ширины свой: объявление живёт в сети, одно на всех
- [x] Обязательность в приёмке не проверяется намеренно: обязательное поле
      не дало бы заполнить профиль жильцам остальных приёмок, идущих рядом.
      Её держат интеграционные фикстуры — запись мимо формы
      (`profile-fields.db-test`) и шаг мастера заселения (`onboarding.db-test`)
- [x] Что значение попадает в собранный договор, проверено интеграционно:
      PDF в приёмке не прочитать (`contracts.db-test`)
