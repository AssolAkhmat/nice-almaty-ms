# Бэкапы базы

Копии базы уезжают на Google Drive — туда же, где документы, но **в другую
папку**. Отдельного хранилища нет: на этом масштабе оно избыточно (решение
владельца, 20 сентября 2026).

## Что защищаем

Утечка серверного токена Drive не должна отдавать читаемый слепок базы.
Поэтому дамп шифруется **до** выгрузки, открытым ключом `age`. На сервере
лежит только открытый ключ (`BACKUP_AGE_RECIPIENT`): сервер умеет зашифровать
и не умеет расшифровать. Закрытый ключ хранится у владельца.

Ключ шифрования бэкапов **не совпадает** с `FIELD_ENCRYPTION_KEY` и не связан
с ним: тот шифрует поля ИИН и УДЛ внутри базы, этот — весь дамп снаружи.

## Как идёт один прогон

`scripts/backup.sh`, запускается из cron хоста в 22:30 UTC — это 03:30
по Алматы (переходов на летнее время там нет).

1. `pg_dump -Fc` из контейнера базы. Версия дампера совпадает с сервером,
   потому что это один и тот же образ.
2. **Проверка восстановления до шифрования.** Дамп разворачивается
   в отдельную базу `nice_almaty_restore_check` в том же контейнере, затем
   одной строкой сверяются числа: миграции, пользователи, дома, счета, аудит.
   Не совпало — прогон падает, и на Drive не уезжает ничего. Проверочная база
   удаляется в любом исходе.
3. Шифрование: `age -r <открытый ключ>`. Результат без заголовка
   `age-encryption.org/v1` дальше не идёт.
4. Выгрузка в папку «Nice Almaty — бэкапы» (`BACKUP_FOLDER_NAME`).
   Папку заводит сам драйвер: область `drive.file` не видит папок, созданных
   владельцем в браузере.
5. **Сверка после выгрузки.** Файл скачивается обратно и сверяется по `sha256`
   с локальным. Обрезанная загрузка без этого выглядела бы успешной.
6. Ротация: `7 + 4 + 6` — семь суточных, по одной на четыре последние недели
   и по одной на шесть последних месяцев. Неделя и месяц считаются по тому,
   что есть в папке, а не по календарю: пропущенный прогон не стоит недельной
   копии. Файлы с чужими именами не удаляются никогда.
7. Незашифрованный дамп на сервере удаляется в любом исходе, включая падение
   посередине: он и есть то, от чего защищает шифрование.

Ротация — чистая функция `scripts/backup-retention.ts`, проверенная числовыми
примерами (`scripts/backup-retention.test.ts`). Она решает, что **удалить**,
и поэтому не проверяется наблюдением за живой папкой.

Повторный прогон в те же сутки перезаписывает копию этого дня: имя файла —
дата, и второй копии за день не заводится. При этом `sha256` зашифрованного
файла у двух прогонов **разный**, даже если дамп побайтно тот же: `age`
шифрует со свежим эфемерным ключом. Сверять копии между прогонами по `sha256`
нельзя — он сверяется только внутри одного прогона, до и после выгрузки.

## Чего сервер проверить не может

Что копия действительно расшифровывается вашим ключом. Для этого нужен
закрытый ключ, а его на сервере нет — в этом и смысл. Поэтому раз в квартал
нужна ваша учебная тревога.

## Учебная тревога (раз в квартал, делает владелец)

Нужны: закрытый ключ `age`, установленные `age` и `psql`, любой postgres 16.

```bash
# 1. Взять свежую копию из папки «Nice Almaty — бэкапы» на Drive.
# 2. Расшифровать своим ключом.
age -d -i ~/nice-almaty-backup-key.txt \
  -o nice-almaty.dump nice-almaty-<дата>.dump.age

# 3. Развернуть в одноразовую базу.
createdb nice_almaty_drill
pg_restore -d nice_almaty_drill --no-owner --exit-on-error nice-almaty.dump

# 4. Сверить числа с живой базой.
psql -d nice_almaty_drill -Atc "select
  (select count(*) from drizzle.__drizzle_migrations)
  || '/' || (select count(*) from users)
  || '/' || (select count(*) from houses)
  || '/' || (select count(*) from accounts)
  || '/' || (select count(*) from audit_log)"

# 5. Убрать за собой.
dropdb nice_almaty_drill && rm -f nice-almaty.dump
```

Дата каждой тревоги записывается ниже, в таблицу. Пустая таблица означает,
что копии ни разу не разворачивали вручную, — а бэкап, который ни разу
не разворачивали, бэкапом не является.

## Где что лежит

| Что | Где |
|---|---|
| Сценарий прогона | `scripts/backup.sh` |
| Шифрование, выгрузка, ротация | `scripts/backup-drive.ts` |
| Правило ротации и его тесты | `scripts/backup-retention.ts` |
| Открытый ключ | `.env`, `BACKUP_AGE_RECIPIENT` |
| Закрытый ключ | у владельца, на сервере его нет |
| Копии | Google Drive, папка «Nice Almaty — бэкапы» |
| Журнал прогонов | `~/nice-almaty-backup.log` на сервере |

## Смена ключа

Старые копии остаются зашифрованными старым ключом: перешифровать их нечем,
закрытого ключа на сервере нет. Поэтому при смене ключа старый **не выбрасывается**,
пока на Drive жива хотя бы одна копия, сделанная им, — то есть минимум полгода
при нынешней ротации.

## Чего здесь нет

- Копий файлов из Drive: документы уже лежат на Drive, и копия копии
  в той же учётной записи ничего не добавляет.
- Оповещения о неудачном прогоне: cron пишет вывод в журнал, ненулевой код
  возврата виден там же. Push-уведомления владельцу появятся, когда будут
  ключи VAPID.
- Потокового шифрования: дамп читается в память целиком. На нынешнем объёме
  это десятки мегабайт; при росте базы шаг придётся переписать на поток.
