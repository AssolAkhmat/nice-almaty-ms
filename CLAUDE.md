# Правила работы над проектом Nice Almaty

Читай этот файл первым в каждой сессии. Он важнее твоих привычек.

## 0. Порядок работы

1. Если установлен плагин **Superpowers** (`/plugin marketplace add obra/superpowers-marketplace`,
   `/plugin install superpowers@superpowers-marketplace`) — работай его циклом:
   `brainstorm → write-plan → execute-plan`, с TDD и code-review субагентами.
   Если не установлен — держи тот же цикл вручную.
2. Перед началом фазы: прочитай `docs/07-ROADMAP.md`, возьми ближайшую незакрытую фазу,
   разбей её на таски и запиши в `docs/tasks/PHASE-N.md` (чек-лист с чекбоксами).
3. Работай **по одному таску**. Один таск = один коммит = зелёные тесты.
4. После каждого таска отмечай чекбокс и обновляй `docs/tasks/PHASE-N.md`.
5. В конце фазы: прогон `pnpm verify`, обновление `docs/08-DECISIONS.md`, отчёт в `PROGRESS.md`.

## 1. Требования — закон

- **Не выдумывай требования.** Источник истины — `docs/`. Если в документации нет ответа:
  выбери самый консервативный вариант, реализуй его и **обязательно** запиши в
  `docs/08-DECISIONS.md` в раздел «Открытые вопросы» строкой
  `[ОТКРЫТО] <вопрос> — принял: <решение> — файл: <путь>`.
- Не удаляй и не «упрощай» описанные требования, чтобы быстрее закрыть таск.
- Не расширяй объём: не добавляй модули, интеграции и экраны, которых нет в ТЗ.

## 3. Технические инварианты

- **Деньги** — целые тенге, тип `bigint` в БД, `number` в TS. Никаких float, никаких копеек.
  Любое деление денег округляется по правилу из `docs/03-BUSINESS-RULES.md` (§0).
- **Даты**: в БД `timestamptz` в UTC; все границы суток, месяцев и «сегодня» считаются
  в зоне `Asia/Almaty` (UTC+5, без переходов). Бизнес-даты (дата ротации, дата заселения) —
  тип `date`, без времени. Утилиты в `src/lib/time.ts`; прямой `new Date()` в бизнес-логике запрещён.
- **Расчётные ядра** (`src/domain/*`) — чистые функции без обращения к БД и без `Date.now()`:
  утилиты, депозит, рейтинг, ротации, счета. Они тестируются числовыми примерами из
  `docs/03-BUSINESS-RULES.md` — **сначала тест, потом код**.
- **Права**: одна точка проверки — `src/lib/authz.ts`. Никаких проверок роли в компонентах.
  Каждый запрос данных обязан быть отфильтрован по `org_id` и, для админа, по `house_id`.
- **Мутации**: server actions для UI + зеркальные обработчики `/api/v1` для ботов,
  общий сервисный слой `src/services/*`. Логику не дублировать.
- **Никакого прямого SQL** в компонентах и роутах — только через `src/db/repositories/*`.

### Создание новой схемы БД — чек-лист

Защита из миграции `0004_lock_down_supabase_data_api` действует **только на схему
`public` и только на объекты роли, от имени которой выполнена миграция**. Это проверено
на живой базе, а не предположено. Поэтому при создании любой новой схемы:

- [ ] Повторить отзыв прав для ролей `anon` и `authenticated` в новой схеме:
      `REVOKE ALL ON ALL TABLES IN SCHEMA <схема>` и
      `ALTER DEFAULT PRIVILEGES IN SCHEMA <схема> REVOKE ALL ON TABLES` —
      блоком, проверяющим существование ролей, как в 0004
- [ ] Убедиться, что схема не попала в список отдаваемых Data API на Supabase
- [ ] Проверить запросом: `select has_schema_privilege('anon', '<схема>', 'USAGE')`
      и `has_table_privilege('anon', '<схема>.<таблица>', 'SELECT')` — оба `false`
- [ ] Миграции выполняются той же ролью, что и раньше: `ALTER DEFAULT PRIVILEGES`
      привязан к роли-создателю объектов, смена роли миграций обнулит защиту

Новая схема безопасна по умолчанию — PostgreSQL не выдаёт на неё прав роли `PUBLIC`,
в отличие от `public`. Опасность появляется в момент, когда схему кому-то открывают
явным грантом: ровно это делает Supabase, когда схему добавляют в Data API.

## 4. Запреты по UI

- Никаких эмодзи в интерфейсе, коде и коммитах.
- Никаких многоцветных градиентов, теней-ореолов, «стеклянных» эффектов, анимаций дольше 200мс.
- Жёлтый `#FEE274` **никогда** не используется как цвет текста на светлом фоне и никогда
  как заливка крупной кнопки. Правила — в `docs/05-DESIGN-SYSTEM.md`.
- Не подключай UI-киты целиком. Собственные компоненты в `src/components/ui/*`,
  примитивы поведения — Radix UI (headless), иконки — lucide-react (одна толщина линии).
- Не используй `tailwind.config.js` — Tailwind v4, конфигурация через `@theme` в `src/app/globals.css`.

## 5. Работа с окружениями

- Ни одна строка бизнес-кода не знает, где она исполняется. Всё через адаптеры (`src/adapters/*`).
- Не используй Node-only API в коде, который может попасть в edge-рантайм.
- Не пиши на файловую систему в проде — только через `StorageProvider`.
- Секреты только из `process.env` через типизированный `src/env.ts` (zod). Никаких значений по умолчанию для секретов.
- Не коммить `.env`. Любую новую переменную добавляй в `.env.example` и в `docs/01-ARCHITECTURE.md`.

## 8. Контракт автономии

Ты идёшь фаза за фазой без участия владельца. Закрыл фазу — обновил `PROGRESS.md`,
разбил следующую на таски и сразу начал её. Плана на подтверждение не жди,
отчёта после фазы не жди: владелец читает `PROGRESS.md` и `docs/08-DECISIONS.md` сам.
ЭКОНОМИЯ КОНТЕКСТА

При старте сессии читай только: CLAUDE.md, PROGRESS.md, docs/BLOCKED.md,
текущий docs/tasks/PHASE-N.md. Документы из docs/ открывай точечно — те,
на которые ссылается текущий таск, и только их. Полное перечитывание
всей документации при каждом запуске запрещено: оно съедает сессию
до начала работы.

PROGRESS.md — состояние, а не журнал. Держи в пределах 40 строк:
где ты сейчас, что закрыто по фазам одной строкой на фазу, что заблокировано.
История живёт в git log и в DECISIONS, дублировать её не нужно.
Разросшийся PROGRESS.md сокращай, а не дописывай.

### Когда останавливаться и спрашивать

Только в этих пяти случаях:

1. **Необратимая потеря данных**: удаление колонки или таблицы с данными,
   деструктивная миграция без обратного пути.
2. **Ослабление модели безопасности**: новый секрет, обход проверки прав,
   отключение защитного правила, публичная ссылка на файл,
   расширение области видимости роли.
3. **Новая внешняя зависимость, меняющая архитектуру**: платный сервис,
   ещё один рантайм, ещё один демон в compose.
4. **Требование в `docs/` противоречит само себе в денежной или правовой части**,
   и оба прочтения дают разный результат в тенге или в договоре.
5. **Критерий приёмки фазы недостижим** без изменения самих требований.

Всё остальное решаешь сам: консервативный вариант, строка `[ОТКРЫТО]`
в `docs/08-DECISIONS.md` в том же коммите, идёшь дальше.
Отсутствие ответа в `docs/` — не повод остановиться.

### Застревание

Один таск — максимум три попытки починки. Не закрылся — заведи запись
в `docs/BLOCKED.md`, пометь таск заблокированным и бери следующий независимый.

**Запись начинается с заголовка `## <таск>`.** По этому маркеру внешний цикл
определяет, что дальше нужен человек: заголовок обязателен и не заменяется списком
или строкой текста.

Образец записи держится здесь, а не в `docs/BLOCKED.md`: цикл читает сырые строки
файла и не разбирает разметку, поэтому пример внутри блока кода остановил бы его
на пустом файле. В `BLOCKED.md` формат описан прозой, без единой строки,
похожей на запись.

Образец приведён без отступа и ровно в том виде, в каком он должен попасть
в файл: сдвинутый на пробелы заголовок цикл не увидит, и блокировка молча
пройдёт мимо человека.

```markdown
## T2.7 — Драйвер Google Drive

- **Что пробовал:** OAuth от имени владельца диска, resumable upload session,
  повторная авторизация с новым refresh_token.
- **Что именно не работает:** загрузка падает с `storageQuotaExceeded`,
  файл не создаётся, ответ одинаков на всех трёх попытках.
- **Чего не хватает от владельца:** подтверждённый доступ к Google-аккаунту
  с квотой либо решение перейти на Shared Drive.
```

Когда таск разблокирован, запись удаляется целиком, а не помечается решённой.

Не переписывай архитектуру, чтобы обойти одну ошибку.
Не оставляй `main` красным: коммит сломал CI — откати его и продолжай с другого конца.

### Возобновление

Каждый коммит оставляет репозиторий в состоянии, из которого новая сессия
поднимается по одной строке:

> Прочитай `CLAUDE.md`, `PROGRESS.md`, `docs/BLOCKED.md` и `docs/tasks/PHASE-N.md`,
> продолжай с первого неотмеченного таска.

`PROGRESS.md` обновляется **каждый раз при закрытии таска**, а не в конце фазы:
где ты сейчас, что закрыто, что заблокировано. Он обязан быть точным
на любой момент времени.

### Обслуживание

Мелочи, которые не стоят прерывания работы, складывай в `docs/tasks/MAINTENANCE.md`.
Разбирай этот список в конце каждой фазы одним коммитом.
